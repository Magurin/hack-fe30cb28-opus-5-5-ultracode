# Soup Kernel Challenge: слитый шаг обучения Qwen2 + NF4 + LoRA на своих Triton-кернелах

Решение для кейса Soup на Decentrathon 6.0. `soup train` (Soup 0.77.0, Qwen2.5-1.5B-Instruct в
NF4, LoRA r=16 на `q_proj`/`v_proj`, batch 4, 64 шага, Kaggle T4) обучает **тот же адаптер** на
**тех же батчах**, но шаг обучения целиком пересобран вокруг наших кернелов: без паддинга, без
fp32-копий активаций, без логитов размером в весь словарь и с весами слоёв, которые ждут своей
очереди в памяти CPU.

## Что сделано и почему

Разбор базового пути на T4 (fp16, без bf16) показал, откуда берутся 14 ГБ и 44% поэлементных
операций в профиле:

1. `prepare_model_for_kbit_training` поднимает всё не-4-битное в fp32, включая общий эмбеддинг /
   `lm_head` (151 936 x 1 536) - весь residual stream идёт в fp32;
2. `bitsandbytes.nn.Linear4bit` приводит выход каждой проекции обратно к fp32, поэтому выходы
   gate/up MLP (токены x 8 960) хранятся для backward в fp32;
3. батч дополняется паддингом до самой длинной строки: при ~205 реальных токенах на строку и
   ~380 по длине батча почти половина работы идёт на pad-токены;
4. логиты `(4, T, 151 936)` существуют в fp16, в fp32 для loss, в виде градиента, копии для
   accuracy - несколько гигабайт на пике.

Поэтому мы не ускоряем отдельные модули HF, а заменяем весь шаг (`solution/engine.py`), сохраняя
математику базы: те же округления до fp16 в тех же местах (выходы проекций, вход attention,
произведение в MLP), fp32 для residual, норм, RoPE, softmax и loss.

1. **Удаление паддинга внутри батча** (разрешено условием). Строки батча упаковываются в одну
   последовательность из N реальных токенов, attention считается varlen-causal по `cu_seqlens`
   встроенным в PyTorch memory-efficient ядром (то же семейство, что SDPA в базе). Батчи и их
   порядок не меняются, строки разных батчей не смешиваются.
2. **Слой декодера = один `torch.autograd.Function`**, который хранит для backward только свой
   вход (fp32 residual, 6 KiB на токен) и пересчитывает forward в backward с теми же seed'ами
   dropout. Это ~6 раз меньше памяти активаций за один лишний проход GEMM qkv, o и gate/up
   (деквантизованные веса в backward нужны всё равно и переиспользуются).
3. **Слитая голова**: final RMSNorm + `lm_head` + cross-entropy + метрики TRL/Soup считаются
   кусками по 256 строк, градиент по скрытому состоянию - в том же проходе. Строки промпта (их
   ~37%) идут отдельными кусками: для них нужны только энтропия и argmax, backward-GEMM через
   матрицу 151 936 x 1 536 для них пропускается.
4. **Веса слоёв в pinned-памяти CPU**: упакованные NF4-байты 28 слоёв (~650 MiB) лежат на хосте и
   копируются на GPU в один из трёх слотов по отдельному CUDA stream на слой вперёд (в backward -
   на слой назад). Копирование (~24 MiB на слой) идёт параллельно с GEMM. После обучения веса
   возвращаются на GPU (`on_train_end`), так что сохранение адаптера видит обычную модель.
5. **Эмбеддинг / `lm_head` в fp16**: peft не поднимает этот замороженный вес в fp32. Это без
   потерь: fp32-значения базы - точные копии fp16-чекпойнта, а `lm_head` база всё равно считает
   под autocast в fp16. Если наш шаг по какой-то причине не включился, fp32-копия
   восстанавливается и обучение идёт исходным кодом Soup.
6. **Компиляция в фоне**: пока Soup читает и квантизует чекпойнт, отдельный поток один раз
   запускает каждый вариант наших кернелов на крошечных тензорах через те же функции, что и шаг
   обучения (ключи кэша Triton совпадают). Компиляция по-прежнему входит в замер, но не
   добавляет к нему: первый шаг идёт 0,5 с вместо 8,5 с. Seed'ы dropout объявлены
   `do_not_specialize`, иначе Triton перекомпилировал бы кернел при seed, кратном 16.

### Наши Triton-кернелы (`solution/kernels.py`)

Ни один не использует `tl.dot`, поэтому решение не зависит от поддержки тензорных ядер Turing
(sm_75) в Triton; GEMM остаются в cuBLAS.

| Кернел | Что делает |
|---|---|
| `nf4_dequant_kernel` | NF4 + двойная квантизация absmax -> fp16 за один проход; побитно совпадает с `bitsandbytes.functional.dequantize_4bit` |
| `rms_fwd_kernel` | [residual add] + RMSNorm в fp32 -> fp16, плюс входы обеих LoRA с dropout (маска - функция seed и позиции, не хранится) |
| `rms_bwd_kernel` | backward RMSNorm с суммой градиентов основной ветки и обеих LoRA (маски регенерируются) и residual-градиентом |
| `qkv_rope_fwd_kernel` | qkv из одного GEMM + LoRA-дельты + RoPE -> q, k, v в раскладке attention |
| `qkv_rope_bwd_kernel` | обратный поворот, сумма градиентов по группам GQA, сборка `[dq \| dk \| dv]` под один GEMM |
| `glu_fwd_kernel` / `glu_bwd_kernel` | SwiGLU над слитым выходом `[gate \| up]` одного GEMM; backward на месте в `[dg \| du]` под один GEMM |
| `lm_head_ce_kernel` | online logsumexp + энтропия + argmax + градиент `softmax - onehot` по словарю 151 936 за два прохода по логитам куска |

Пример из шаблона (`swiglu.py`) удалён: наши GLU-кернелы работают над другим (слитым) layout и
по метрике `check_rules.py` похожи на пример на 0,65-0,70 (порог ручной проверки 0,8).

### Источники идей (код написан нами)

- Fused RMSNorm, chunked "fused linear cross-entropy": [Liger-Kernel](https://github.com/linkedin/Liger-Kernel),
  [Unsloth](https://github.com/unslothai/unsloth), [Cut Cross-Entropy (Wijmans et al., 2024)](https://arxiv.org/abs/2411.09009).
- Online softmax / logsumexp: Milakov, Gimelshein, [arXiv:1805.02867](https://arxiv.org/abs/1805.02867).
- NF4 и двойная квантизация: QLoRA, Dettmers et al., [arXiv:2305.14314](https://arxiv.org/abs/2305.14314), формат `bitsandbytes`.
- Пересчёт активаций: Chen et al., [arXiv:1604.06174](https://arxiv.org/abs/1604.06174); подкачка весов с хоста - идея
  ZeRO-Offload / ZeRO-Infinity ([arXiv:2101.06840](https://arxiv.org/abs/2101.06840)).
- Varlen attention без паддинга: FlashAttention varlen API ([arXiv:2205.14135](https://arxiv.org/abs/2205.14135));
  у нас - встроенное в PyTorch ядро `_efficient_attention_forward/backward` с `cu_seqlens`.

## Как подключается и что остаётся прежним

`solution.apply()` (вызывается harness до сборки модели) ставит три патча (`solution/patch.py`):

- `SFTTrainerWrapper.setup` - запускает фоновую компиляцию кернелов;
- `peft.prepare_model_for_kbit_training` - оставляет эмбеддинг Qwen2 в fp16 (см. выше);
- `SFTTrainerWrapper.train` - если модель распознана (Qwen2 + bnb NF4 + LoRA на q/v), подменяет
  `compute_loss` тренера. Новый `compute_loss` выполняет ту же бухгалтерию, что HF `Trainer` +
  TRL `SFTTrainer` + rewind-рекордер Soup: нормировка loss по `num_items_in_batch`, `entropy` по
  всем реальным токенам, `num_tokens`, `mean_token_accuracy` по токенам ответа, строки
  `rewind.jsonl` с loss по каждой строке.

Не меняются: модель, данные, батчи и их порядок, число шагов, LoRA (r, alpha, dropout 0,05,
целевые модули), оптимизатор и расписание lr, настройки тренера, выходы Soup, аллокатор. Всё
нераспознанное (фейковые модули в тестах Soup, eval-режим, другие архитектуры) уходит в
исходный код без изменений. Обучаемых параметров не добавляется: градиенты LoRA возвращает наш
`autograd.Function`, оптимизатор тот же.

## Как запустить

### Kaggle (как жюри)

1. Create -> New Notebook -> File -> Import Notebook -> `templates/kaggle_notebook.ipynb`.
2. Справа: Accelerator **GPU T4 x2**, Internet **on**.
3. В первой ячейке `REPO_URL` = этот репозиторий, `COMMIT` = финальный коммит (см. выше).
4. Run All (~10 минут). Итог печатает `harness/run_task.py`, проверки - `harness/check_rules.py`.

### Локально (Linux + CUDA GPU)

```bash
pip install "soup-cli[train]==0.77.0" "transformers==5.16.1" "peft==0.20.0" "trl==0.29.1" \
    "bitsandbytes==0.50.2" "accelerate==1.14.0" pytest
python task/prepare_data.py
python -m pytest solution -q          # кернелы против PyTorch и весь шаг против HF + PEFT
python harness/run_task.py --repeats 2
python harness/check_rules.py
```

На Ampere и новее Soup обучает в bf16 - это другой путь, наш шаг рассчитан на fp16-путь T4.

### Тесты корректности (`solution/test_kernels.py`)

- каждый кернел против PyTorch, forward и backward;
- NF4-деквантизация побитно против `bitsandbytes`;
- varlen attention против SDPA по каждой строке;
- **весь шаг против HF + PEFT под fp16 autocast** на маленькой 4-битной Qwen2: loss совпадает до
  2e-6, градиенты LoRA - до 0,1-0,5% (уровень шума fp16);
- стриминг весов: loss и градиенты побитно те же, `restore` возвращает веса побитно.

## Ограничения и что не получилось

- Решение заточено под этот кейс: Qwen2 (RoPE `default`, без sliding window), веса NF4 из
  bitsandbytes, LoRA только на `q_proj`/`v_proj`, fp16-путь. В остальных случаях работает исходный
  код Soup (без ускорения).
- Пересчёт слоя в backward стоит ~+20% времени цикла обучения в обмен на ~6x меньше памяти
  активаций; это сознательный выбор под формулу баллов (логарифм отношения памяти растёт
  быстрее, чем теряется на скорости).
- Ниже ~1,15 ГБ (плюс CUDA-контекст) пик не опускается: столько занимает загрузка модели
  в transformers ещё до обучения; трогать загрузчик мы не стали.
- Время вне цикла обучения (импорты, загрузка и токенизация данных, загрузка модели) - то же, что
  у базы; мы его не ускоряли.
- GEMM занимают ~80% GPU-времени шага; свой fused NF4-GEMM на Triton для sm_75 мы не делали.
- Энтропия и loss по строкам считаются в fp32 (в базе часть этих величин округляется до fp16):
  расхождение с базой - сотые доли процента, в допусках проверки 5.
