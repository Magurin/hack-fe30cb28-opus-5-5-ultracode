# Soup Kernel Challenge: слитый шаг обучения Qwen2 + NF4 + LoRA на своих Triton-кернелах

Решение кейса Soup на Decentrathon 6.0. Команда `soup train` (Soup 0.77.0,
Qwen2.5-1.5B-Instruct в NF4, LoRA r=16 на `q_proj`/`v_proj`, batch 4, 64 шага, Kaggle T4, fp16)
обучает **тот же адаптер на тех же батчах**, но шаг обучения пересобран вокруг наших
Triton-кернелов: без паддинга, без fp32-копий активаций, без логитов на весь словарь, с пересчётом
слоя в backward. Замороженные веса на GPU не живут: NF4-веса слоёв и общий эмбеддинг / `lm_head`
с момента загрузки модели лежат в pinned-памяти CPU и подкачиваются на GPU по мере надобности.
Туда же уходят и входы слоёв, и выходы GEMM `[gate | up]`, которые шаг хранит для backward, а на
быстрой шине (Kaggle) - и тензоры attention этих слоёв (q, k/v, выход attention и `o_proj`).

| | База Soup 0.77.0 | Решение | Отношение |
|---|---|---|---|
| Время всей команды `soup train`, Kaggle T4, `--repeats 2` (среднее) | 79,4 с | 43,5 с | speedup **1,824x** |
| из него цикл обучения, 64 шага | 55,3 с | 24,0 с | 2,31x |
| Пик памяти GPU (nvidia-smi, весь процесс) | 14 345 MiB | 583 MiB | **24,61x** меньше |
| Eval loss на публичных строках | 2,04967 | 2,04967 | 0,000% |
| `harness/check_rules.py` | | | 10 из 10 проверок |

памяти, как в формуле баллов (ТЗ, 11.2). r2 - `run_task.py --repeats 2`, как у жюри (база, решение,

## Архитектура за 5 минут

`solution.apply()` вызывается harness до сборки модели. Он ставит патчи (`solution/patch.py`), и
в начале `SFTTrainerWrapper.train` подменяет `compute_loss` тренера на наш слитый шаг
(`solution/engine.py`), если модель распознана (Qwen2 + bitsandbytes NF4 + LoRA на q/v) и Soup
обучает в fp16 на GPU класса T4. Тренер HF,
оптимизатор, GradScaler, расписание lr, логирование и выходы Soup остаются своими.

Загрузка модели (до первого шага):

```
transformers / bitsandbytes грузят Qwen2 как обычно, но
  эмбеддинг / lm_head (fp16, 445 MiB)  -> сразу в память CPU (offload.py), на GPU не попадает
  каждый Linear4bit: квантуется в NF4 на GPU тем же кодом bnb -> упакованные байты и absmax
                     сразу копируются на хост, копия на GPU освобождается (hostload.py)
итог: на GPU только нормы, bias q/k/v и маленькое состояние двойной квантизации
(LoRA peft создаёт рядом с весом на CPU, на GPU её переносит установка шага)
```

Один шаг обучения:

```
батч 4 x L с паддингом справа
  -> упаковка: N реальных токенов подряд + cu_seqlens (паддинга нет, строки не смешиваются)
  -> эмбеддинг: строки берутся из fp16-таблицы на CPU, копируются на GPU -> fp32 residual
  -> 28 x _Layer (autograd.Function; для backward хранит свой вход - fp32 residual, 6 KiB на
       токен, ждёт в pinned-памяти CPU - и выход [gate|up], на хосте или, если позволяет
       потолок шага, на GPU; остальное пересчитывает)
       WeightStream: NF4-байты следующего слоя едут с хоста на GPU по отдельному CUDA stream
                     (2 слота на GPU)
       InputStream:  выход слоя пишется сразу в слот кольца (3 слота на GPU) и копируется
                     на хост по своему stream, пока следующий слой считает
       GuStream:     GEMM [gate|up] пишет прямо в слот своего кольца (2 слота), оттуда
                     выход едет на хост - в backward этот GEMM не повторяется; слои, которые
                     держат [gate|up] на GPU, считают этот GEMM двумя половинами (gate, up)
       AttnStream:   q, k/v (2 KV-головы), выход attention и o_proj тех же слоёв - тоже на
                     хост (2 слота), если шина host->GPU >= 9 ГБ/с (замер на первом шаге)
       nf4_dequant  [q|k|v], o, [gate|up], down  -> fp16
       rms_fwd      RMSNorm (перед MLP - вместе с residual add) + входы LoRA с dropout
                    (маски - бит в бит как у базы)
       GEMM qkv (cuBLAS) -> qkv_rope_fwd (LoRA-дельты + RoPE) -> varlen attention (PyTorch, cu_seqlens)
       GEMM o -> rms_fwd -> GEMM [gate|up] -> glu_fwd (SwiGLU) -> GEMM down -> + residual
  -> голова (HostHead): lm_head едет с хоста кусками по 8 192 строки словаря (3 буфера по 24 MiB),
       копии в 2 буфера начинаются ещё на последних слоях forward, третий берётся в начале
       головы; на каждый кусок:
       GEMM lm_head (cuBLAS) -> lm_head_piece (online logsumexp, энтропия, argmax, exp(logit - max)
       для градиента; сам градиент по скрытому состоянию копит GEMM cuBLAS); в конце
       lm_head_finish: loss, метрики, градиент.
       Логиты на весь словарь не существуют ни в какой момент
backward, слой 27 -> 0:
  веса подкачиваются в обратном порядке, входы слоёв - за 2 слоя до своего backward
  (последние 3 ещё в кольце), [gate|up] и тензоры attention - за 1 слой; из forward слоя
  пересчитываются только две RMSNorm (без AttnStream - ещё GEMM qkv / o, RoPE и attention,
  но не GEMM [gate|up]; или "экономно" - решает прогноз пика шага, см. ниже),
  дальше *_bwd-кернелы и GEMM cuBLAS; градиенты LoRA возвращает наш autograd.Function
```

Четыре решения, из которых всё следует:

1. **Заменяем весь шаг, а не отдельные модули HF.** Память базы съедают не веса, а то, что модули
   HF хранят между собой: fp32-выходы проекций bitsandbytes, полные логиты TRL, паддинг. Убрать это
   можно только на уровне всего шага.
2. **Математика базы сохраняется.** Округления до fp16 в тех же местах (выходы проекций, вход
   attention, произведение в MLP), fp32 для residual, норм, RoPE, softmax и loss; маски LoRA
   dropout - бит в бит те же, что у базы. Отсюда кривая loss в среднем в 0,01% от базы, на отдельных
   шагах - до ~0,05%.
3. **GEMM остаются в cuBLAS, всё между ними - наши кернелы.** На T4 (sm_75) `tl.dot` в Triton 3.6 не
   использует тензорные ядра (~1 TFLOPS против 16-34 у cuBLAS, замер), поэтому свой GEMM - проигрыш.
   Выигрыш - в слиянии поэлементных операций и приведений dtype, которые в базе занимают ~44% профиля.
4. **Замороженное и отложенное - на CPU, на GPU только то, что считается сейчас.** NF4-веса
   (~645 MiB) и эмбеддинг / `lm_head` (445 MiB) уходят на хост ещё при загрузке модели, а на GPU
   приезжают кусками на время своего GEMM; входы слоёв, выходы `[gate | up]` и (на быстрой шине)
   тензоры attention ждут backward там же (на Kaggle копия по шине дешевле, чем повторить самый
   тяжёлый GEMM и attention). Шаг сам прогнозирует
   свой пик и держится под потолком памяти (340 MiB allocated), а запас под ним тратит на хранение
   активаций вместо пересчёта.

### Наши Triton-кернелы (`solution/kernels.py`)

Доля - время кернела (CUDA events harness) от времени обучения, шаги 3-64; Kaggle T4, коммит
`8c584c0`, публичные строки, меньший из двух запусков `--repeats 2` (у кода `5f9b2ef` на Brev T4 -
13,9-15,0%: другие процессор и шина).
Ни один кернел не использует `tl.dot`.

| Кернел | Что сливает (что заменяет в базе) | Доля |
|---|---|---|
| `nf4_dequant_kernel` | NF4 + двойная квантизация absmax -> fp16 за один проход, побитно как `bitsandbytes.functional.dequantize_4bit` (у bnb - 2 кернела); один запуск на [q\|k\|v] и один на [gate\|up] (у слоёв, держащих `[gate \| up]` на GPU, - по половине перед каждой половиной GEMM) | 9,5% |
| `rms_fwd_kernel` | RMSNorm в fp32 -> fp16 (перед MLP - вместе с residual add) + входы обеих LoRA с dropout; маска бит в бит как у `nn.Dropout` базы: кернел считает тот же поток Philox, что `fused_dropout` PyTorch, от seed и смещения генератора CUDA, и маску не хранит; в базе 5-6 операций PyTorch и касты | 2,7% |
| `rms_bwd_kernel` | backward RMSNorm, сумма градиентов основной ветки и обеих LoRA (те же маски: тот же seed и смещение), residual-градиент | 1,5% |
| `qkv_rope_fwd_kernel` | разрезка qkv одного GEMM, LoRA-дельты, RoPE -> q, k, v в раскладке attention; k/v сразу расширены под GQA | 1,25% |
| `qkv_rope_bwd_kernel` | обратный поворот, сумма градиентов по группам GQA, сборка `[dq \| dk \| dv]` под один GEMM | 0,45% |
| `glu_fwd_kernel` | SwiGLU над слитым выходом `[gate \| up]` одного GEMM (в базе - fp32 silu * up) | 1,5% |
| `glu_bwd_kernel` | backward SwiGLU на месте в `[dg \| du]` под один GEMM | 2,7% |
| `lm_head_piece_kernel` | голова по кускам словаря: online-состояние каждой строки (максимум, сумма exp, сумма exp * logit, лучший логит и его индекс) переносится от куска к куску; для строк с целевым токеном пишет exp(logit - max) под GEMM градиента и множитель пересчёта накопленного; вынимает строку веса целевого токена. Заменяет fp32-логиты, cross-entropy, entropy и accuracy TRL, loss строк для rewind | 0,70% |
| `lm_head_finish_kernel` | после последнего куска: loss, энтропия, accuracy и градиент по скрытому состоянию `acc / s - W_target` в fp16 | 0,01% |
| `lm_head_ce_kernel` | та же голова за один проход по всему словарю, когда вес `lm_head` на GPU (`OFFLOAD_HEAD = False`); блоки и операции у `lm_head_piece_kernel` те же, поэтому при тех же логитах loss, энтропия и accuracy совпадают побитно | - |
| `torch_dropout_keep_kernel` | маска dropout PyTorch по тем же формулам, что в `rms_*_kernel`, - для тестов против `F.dropout` и отладочного зонда масок (`dev/mask_probe`); в обучении не запускается | - |
| **Вместе** | проверка 4 требует >= 5% | **20,2%** |

Проверка 3 перечисляет и `lm_head_ce_kernel`: harness считает запуском каждый вызов
`JITFunction.run`, в том числе `kernel.warmup(...)`, которым фоновый прогрев (`solution/warmup.py`)
компилирует кернел для запасного пути с весом головы на GPU. В шагах обучения при
`OFFLOAD_HEAD = True` он не запускается, поэтому в доле времени его нет.

Пример из шаблона (`swiglu.py`) удалён: наши GLU-кернелы работают над другим (слитым) layout и по
метрике `check_rules.py` похожи на пример на 0,65-0,70 (порог ручной проверки 0,8).

### Источники идей (код написан нами)

- Fused RMSNorm и chunked "fused linear cross-entropy": [Liger-Kernel](https://github.com/linkedin/Liger-Kernel),
  [Unsloth](https://github.com/unslothai/unsloth), [Cut Cross-Entropy (Wijmans et al., 2024)](https://arxiv.org/abs/2411.09009).
- Online softmax / logsumexp: Milakov, Gimelshein, [arXiv:1805.02867](https://arxiv.org/abs/1805.02867).
- NF4 и двойная квантизация: QLoRA, Dettmers et al., [arXiv:2305.14314](https://arxiv.org/abs/2305.14314), формат `bitsandbytes`.
- Пересчёт активаций: Chen et al., [arXiv:1604.06174](https://arxiv.org/abs/1604.06174).
- Подкачка весов с хоста, в том числе головы кусками словаря: ZeRO-Offload / ZeRO-Infinity ([arXiv:2101.06840](https://arxiv.org/abs/2101.06840)).
- Attention без паддинга: FlashAttention varlen API ([arXiv:2205.14135](https://arxiv.org/abs/2205.14135));
  у нас - встроенное в PyTorch ядро `_efficient_attention_forward/backward` с `cu_seqlens`.

T4 на Kaggle шумит по времени: от инстанса и нагрева база шла от 79 до 97 с, поэтому версии мы
сравниваем только внутри одной сессии, а время между машинами не сравниваем. Память стабильна:
на публичных строках пик решения 635 MiB во всех прогонах `6b1cc09` (Brev), 637-639 с `[gate | up]`
на хосте, 577-601 со стеком CUDA 16 байт (601 на Kaggle); до выгрузки входов слоёв - 813 MiB во всех прогонах
`5c93f07` и `180c8e4`, ещё раньше 1 275-1 277.

**Почему время на Kaggle гуляет: T4 работает в пределе мощности 70 Вт.** Мы сняли `nvidia-smi -lms
100` во время серии r2 и ещё трёх запусков решения (Kaggle, `777b83a`). Под нагрузкой power cap
активен 100% времени и у базы, и у решения, тепловых причин троттлинга нет, температура до 81 C.
При фиксированных 70 Вт частота SM падает с нагревом: внутри запуска решения ~860 -> ~750 МГц, от
запуска к запуску цикл 26,75 -> 28,22 с (+5,5%), вся команда 50,3-52,4 с.

Наш шаг плотнее по энергии, чем база: SM под нагрузкой 770-830 МГц против 960-1 115. Сильнее всего
в предел упирается GEMM (на горячем GPU GEMM `[gate | up]` идёт на ~680 МГц), копии по шине до
него не доходят (~43 Вт). Поэтому самая дорогая статья шага - GEMM пересчёта (см. п. 4 "Что сделано").

У жюри решения идут 2-м и 3-м, на уже прогретом GPU, а холодный первый запуск сессии (+~10 с вне
цикла) достаётся базе. Сессии Kaggle различаются и по процессору: вне цикла 19-21 с в одних и 23-24 с
в других. Поэтому наши r2-замеры одним и тем же ноутбуком, начиная с `180c8e4`, лежат от 1,598x до 1,824x;
до своей токенизации последние семь сессий давали 1,698-1,729x (история версий
ниже), а сравнивать версии можно только внутри одной сессии.

**Куда уходит время шага на Kaggle** (T4, `e897223`, шаги 16-25; py-spy и torch.profiler снаружи
нашего кода). Шаг упирается в GPU, а не в процессор. Главный поток Python около трёх четвертей
шага (~0,4 с) ждёт GPU: пока поток autograd выполняет backward (~120 мс), в проверке loss на NaN у
тренера HF, которая синхронизируется с концом шага (~120 мс), и в одной синхронной копии константы
в голове (~80 мс; убрана в `41ee222` - начальное состояние строк головы теперь заполняется на GPU,
выходы головы побитно те же). Собственная работа Python - ~47 мс на шаг в главном потоке и ~30 мс в потоке
backward: запуски кернелов, наш шаг, тренер и оптимизатор. GPU занят 95-96% времени (nvidia-smi)
и всё время в пределе мощности 70 Вт; простои - щели между запусками кернелов (~9-13 мс на шаг) и
граница шага в коде HF / Soup / харнесса (~15-17 мс), а не ожидание копий по шине (~8 мс).
Поэтому главный рычаг скорости - меньше работы GPU (пересчёт, распаковка NF4, GEMM), а не меньше
Python. Пример: 8 самых длинных шагов публичных строк (1 282-1 427 токенов) не помещали кольцо
`[gate | up]` под потолок и пересчитывали этот GEMM во всех слоях (~+100 мс на шаг); с кусками
`[gate | up]` на хосте (`03b9441`) вся команда на Kaggle быстрее на 0,45-0,82 с (A/B).

260 -> те же 555 MiB (пол экономного шага) и цикл 28,35 с. Взяли 420: -160 MiB за 0,4 с цикла на Brev.

320 / 300 упираются в ту же фрагментацию (reserved 346), а 270 на Kaggle отправил длинные шаги в
экономный путь с пересчётом (+6 с цикла, см. int8 `[gate | up]` в отвергнутых).

**Почему "максимум памяти", а не "освобождённое - на скорость".** Баллы: скорость
35 x ln s / ln s_лучш, память 30 x ln m / ln m_лучш (ТЗ, 11.2). Можно было держать пик ~1 233 MiB и
отдать 445 MiB шагам под хранение активаций, но на T4 это мало ускоряет: кривая `EXTRA_MEMORY_MIB`
тогдашнем коде даёт -1,8 с за +512 MiB (m 11,25 -> 8,28) и -2,9 с за +1 024 MiB. Выгрузки головы
и входов слоёв на Kaggle стоят вместе до ~0,9 с (A/B в одной сессии, цифры - в "Гипотезах и
экспериментах"), это ~0,8 балла скорости при лидере s = 2,2, а память растёт с m 11,6 до 22,6
(цифры m - на момент решения, `6b1cc09`; сейчас ~31 по A/B на Kaggle):

| Сценарий у лучших конкурентов | Без выгрузок на хост (m 11,6) | Веса и голова (m 17,6) | + входы слоёв (m 22,6) |

| по памяти лучше нас никого (m < 11,6) | память 30 | память 30 | память 30, при равной сумме баллов выше команда с лучшей памятью (ТЗ, 11.2) |

Риск: если у машины жюри шина медленная, как у Brev, выгрузки головы и входов стоят ~3 с (s 1,65 ->
~1,53 на Brev, замер `6b1cc09`), то есть ~3 балла за скорость при лидере s = 2,2. Ноутбук жюри - Kaggle, где их
цена в пределах разброса запусков, поэтому этот риск мы приняли.

Тот же расчёт решил и последний шаг, 543 -> 463 MiB. Около нашего пика -20 MiB дают ~0,35 балла
памяти (30 / ln m_лучш x 20 / 500 при m_лучш ~31) - примерно столько же, сколько 0,4 с стены по
скорости; пакет памяти стоил ~+0,3 с за -80 MiB, то есть около +1 балла.

## Что сделано и почему

Разбор базового пути на T4 (fp16, без bf16) показал, откуда 14 ГБ и ~44% поэлементных операций в
профиле:

1. `prepare_model_for_kbit_training` поднимает всё не-4-битное в fp32, включая общий эмбеддинг /
   `lm_head` (151 936 x 1 536) - весь residual stream идёт в fp32;
2. `bitsandbytes.nn.Linear4bit` приводит выход каждой проекции обратно к fp32, поэтому выходы
   gate/up MLP (токены x 8 960) хранятся для backward в fp32;
3. батч дополняется паддингом до самой длинной строки: при ~205 реальных токенах на строку и
   ~380 по длине батча почти половина работы идёт на pad-токены;
4. логиты `(4, T, 151 936)` существуют в fp16, в fp32 для loss, в виде градиента и копии для
   accuracy - несколько гигабайт на пике.

Что мы с этим сделали:

1. **Удаление паддинга внутри батча.** Строки батча упаковываются в одну последовательность из N
   реальных токенов, attention считается varlen-causal по `cu_seqlens` встроенным в PyTorch
   memory-efficient ядром (то же семейство, что SDPA в базе). Батчи и их порядок не меняются, строки
   разных батчей не смешиваются, `num_tokens` = сумма `attention_mask`.
2. **Слой декодера = один `torch.autograd.Function`**, который хранит для backward только свой вход
   (fp32 residual, 6 KiB на токен) и пересчитывает forward в backward с теми же масками dropout.
   Это ~6x меньше памяти активаций за лишний проход GEMM qkv, o и gate/up (деквантизованные веса в
   backward нужны всё равно). Градиент по входу `down_proj` считается до пересчёта, поэтому слой не
   держит все четыре распакованных веса сразу (-27,5 MiB на пике). Что из этого теперь не
   пересчитывается и где ждёт - п. 3-6.
   Маски LoRA dropout - бит в бит как у базы (`98627c5`): PEFT вызывает `nn.Dropout` на входе LoRA
   каждого модуля по порядку (слой 0 q, слой 0 v, слой 1 q, ...), и каждый вызов берёт у генератора
   CUDA seed и смещение Philox и сдвигает смещение. `TorchDropout` берёт и сдвигает их так же, а
   `rms_fwd` / `rms_bwd` считают по ним тот же поток Philox, что `fused_dropout` PyTorch (fp32,
   сетка по формуле ATen); backward переигрывает тот же (seed, смещение), памяти маски не нужно.
   Первый шаг сверяет наш кернел с `torch._fused_dropout` на отдельном генераторе; если маски
   разошлись бы, каждый шаг уходит в код Soup (`UnsupportedBatch`). Раньше маски давал наш
   генератор в кернеле - статистически те же, но не бит в бит; на такой вопрос организаторы
   ответили "нет" ([t.me/souptasterschat/2596](https://t.me/souptasterschat/2596), ответы
   [t.me/souptasterschat/2632](https://t.me/souptasterschat/2632) п. 2 и
   [t.me/souptasterschat/2637](https://t.me/souptasterschat/2637)), и мы перешли на маски базы.
   Проверка на настоящей модели, в том числе на Kaggle: 168 из 168 масок за 3 шага бит в бит,
   состояние генератора CUDA (seed, смещение) после шагов 1-3 - (1, 2016), (1, 4928), (1, 9408), как
   у базы.
3. **Входы слоёв в pinned-памяти CPU** (`6b1cc09`, `InputStream` в `solution/engine.py`).
   - Что: после п. 2 главное, что шаг хранит для backward, - входы 28 слоёв, 28 x N x 6 KiB
     (~135 MiB на батче в 820 токенов, ~330 MiB на 4 x 512). Они ждут backward на хосте.
   - Как: слой пишет свой выход сразу в слот кольца из трёх слотов на GPU (мимо кэширующего
     аллокатора, который такие блоки фрагментировали); копия на хост идёт по своему CUDA stream,
     пока следующий слой считает; в backward вход возвращается в свой слот за два слоя до того, как
     нужен.
   - Цифра: пик 813 -> 735 MiB, с потолком шага 420 MiB - 635 (раздел про память; со всеми
     следующими шагами сейчас 463 на Kaggle).
   - Проверка: копии fp32 -> fp32, loss и градиенты LoRA побитно те же, что со входами на GPU
     (тест). Выключатель - `OFFLOAD_ACTIVATIONS`.
4. **`[gate | up]` в pinned-памяти CPU вместо пересчёта** (`869380e`, `GuStream`).
   - Что: самая дорогая часть пересчёта в backward - GEMM `[gate | up]` (~82% FLOP пересчёта qkv, o и
     gate/up). Слои, которые
     не держат его выход на GPU по плану шага (п. 6), отправляют выход на хост (35 KiB на токен и
     слой, буфер 1,9 ГиБ под 2 048 токенов), и в backward этот GEMM не повторяется.
   - Как: GEMM пишет прямо в слот кольца из двух слотов (`mm(out=)`), копия на хост - по своему
     stream, в backward выход возвращается за слой до того, как нужен; общий код колец с
     `InputStream` - класс `_HostRing`. Кольцо учтено в прогнозе пика.
   - Длинные шаги (`03b9441`): если кольцо целых выходов `[gate | up]` не помещается под потолок (на
     публичных строках 8 шагов из 64, 1 282-1 427 токенов), шаг берёт кольцо кусков по 512 токенов
     (2 x 18 MiB): MLP таких слоёв идёт кусками, куски уходят на хост и возвращаются в backward.
     Раньше такой шаг пересчитывал `[gate | up]` во всех слоях (~+100 мс на шаг на Kaggle). Результат
     побитно как у кускового MLP экономного шага (тест), но не как у целого GEMM - cuBLAS суммирует
     куски в другом порядке. Экономные шаги (п. 7) пересчитывают, как раньше: копировать им
     `[gate | up]` всех слоёв (2 ГБ в каждую сторону на 2 048 токенов) на T4 было на 10 с дольше.
     Kaggle A/B против `12029b6`: -0,45..-0,82 с на всю команду, пик тот же.
   - Цифра: на Kaggle -1,7..-2,6 с на всю команду (A/B в одной сессии, дважды), на Brev +~5 с. На
     Kaggle выигрыш больше сэкономленного вычисления (24 мс/шаг при равных частотах), потому что T4
     там в пределе мощности, а GEMM пересчёта сжигает её больше всего (раздел "Kaggle T4").
   - Подготовка: закрепить 1,9 ГиБ - ~0,95 с, поэтому отдельный поток (`warmup.py`, nice 19) во время
     загрузки модели заводит страницы буфера как обычную память, а первый шаг только регистрирует их
     на месте (`cudaHostRegister`, ~0,1 с; `9de39df`).
   - Проверка: на шагах с кольцом целых выходов loss и градиенты LoRA побитно те же, что с
     пересчётом; длинные шаги с кусками - побитно как кусковой MLP экономного шага (тесты).
     Выключатель - `OFFLOAD_GU`.
5. **Тензоры attention в pinned-памяти CPU вместо пересчёта** (`dd26add` - `9d31eea`, `c0819ae`,
   `7724ae2`, `AttnStream`).
   - Что: после п. 4 backward слоя с готовым `[gate | up]` всё ещё пересчитывал перед собой две
     RMSNorm, GEMM qkv и o, RoPE и attention (~20 мс шага T4). Теперь q, k, v (k / v - их 2
     KV-головы, а не расширенные под GQA), выход attention и выход `o_proj` таких слоёв ждут
     backward на хосте (10 KiB на токен и слой в каждую сторону), а backward повторяет только две
     RMSNorm (входы LoRA с теми же масками dropout и residual после attention).
   - Как: кольцо из двух слотов на GPU (общий `_HostRing`), подкачка за слой до backward, как у
     `GuStream`; logsumexp attention и seed'ы остаются на GPU (несколько KiB на слой), k / v
     расширяются под GQA прямо перед backward attention. Кольцо учтено в прогнозе пика и берётся
     только рядом с кольцом целых выходов `[gate | up]`: рядом с кольцом кусков длинного шага копии
     обоих сделали стресс 4 x 512 на T4 на 10 с дольше и пик на 42 MiB выше (581 против 539 MiB,
     `7724ae2`). С `c0819ae` - для всех слоёв такого шага, в том числе держащих `[gate | up]` на GPU.
     Буфер на хосте (560 MiB под 2 048 токенов) заводится в фоне во время загрузки и закрепляется на
     месте первым шагом, как у `GuStream`.
   - Только на быстрой шине (`9d31eea`): на первом шаге решение меряет копию host -> GPU (4 x 16 MiB
     из pinned NF4-весов) и включает AttnStream при `ATTN_MIN_GBPS` = 9 ГБ/с и выше. В `train.log`
     пишется `[solution] host-to-GPU copies at X GB/s: attention tensors in host memory` (или
     `recomputed`). На Kaggle мы видели 10,1-12,3 ГБ/с - включено; на Brev 6,3 ГБ/с - выключено:
     там копии стоили +4 с. Если сессия Kaggle окажется медленнее порога, attention просто
     пересчитывается, как раньше: меняется только время.
   - Цифра: Kaggle A/B против `8c584c0` на двух аккаунтах по 3 раунда: вся команда -0,96 / -0,56 /
     -0,75 с и -0,30 / -0,46 / -0,46 с, пик 583 -> 563 MiB.
   - Проверка: loss и градиенты LoRA побитно как с пересчётом (тесты, в том числе длинный шаг, шаг
     с кусками `[gate | up]`, экономный шаг и граница, где кольцо `[gate | up]` помещается под
     потолок, а оба кольца - нет). Выключатель - `OFFLOAD_ATTN`.
6. **Адаптивный пересчёт.** В начале шага прогнозируем его пик по уже выделенной памяти и числу
   токенов N (модель из размерностей сети; сверена с замером по всем шагам, тогда ещё со входами
   слоёв на GPU: реальный пик - 65 MiB + 218 KiB на токен над началом шага, прогноз держится на
   46 MiB + 14 KiB/токен выше). В запас под
   потолком шага (340 MiB allocated, `STEP_CAP_MIB`; как он выбран - в разделе про память) кладём
   выход GEMM `[gate | up]` последних k слоёв - для них самый тяжёлый GEMM пересчёта не повторяется.
   На эти слои и приходится пик шага, поэтому они считают GEMM `[gate | up]` двумя половинами -
   gate, потом up, каждый вес распаковывается прямо перед своей половиной: на пике жива половина
   веса 52,5 MiB, а cuBLAS пишет половины в свои столбцы - побитно как один GEMM (`222533f`).
   Если на коротком батче gate/up уже хранится у всех слоёв, остаток идёт на остальные
   промежуточные тензоры (такие слои не пересчитывают ничего). На T4 цикл стал на 14-20% быстрее,
   пик не изменился. Без явного потолка (`STEP_CAP_MIB = None`) он считается от пика загрузки минус
   `KEEP_MARGIN` (112 MiB на фрагментацию аллокатора и модули CUDA, подгружаемые во время обучения),
   и тогда `EXTRA_MEMORY_MIB` позволяет шагам занимать память сверх него (кривая - в экспериментах).
7. **Экономный шаг для самых длинных батчей** (`fbe7502`). Если даже без хранения шаг выше
   потолка (при тогдашнем потолке и входах на GPU это ~1 870+ токенов в батче, ~5% случайных срезов;
   на стресс-срезе 4 x 512 режим работает и сейчас), пересчёт идёт в две части:
   сначала до входа MLP, после backward MLP - attention ещё раз для своего backward; MLP считается
   кусками по 512 токенов, так что `[gate | up]` живёт кусками. На батче 4 x 512 пик шага над его
   началом 570 -> 477 MiB, allocated 1 134 -> 1 041 MiB (ниже тогдашнего потолка 1 116). Цена - второй
   пересчёт attention (+9% к циклу на стресс-срезе, где такие все шаги); на обычных шагах режим не
   включается, их результат побитно тот же.
8. **Слитая голова кусками словаря** (`5c93f07`). Вес `lm_head` (151 936 x 1 536) лежит на хосте
   и едет на GPU кусками по 8 192 строки словаря в три буфера по отдельному CUDA stream; первые
   копии - в два буфера из трёх - стартуют ещё на последних слоях forward, третий берётся в начале
   головы (`0c0c954`): пик шага приходится на forward последних слоёв, и там он на 24 MiB ниже.
   Для каждого куска: GEMM `lm_head` (cuBLAS)
   по всем строкам шага, затем `lm_head_piece_kernel` обновляет online-состояние каждой строки
   (максимум, сумма exp, сумма exp * logit, argmax) и для строк с целевым токеном пишет
   exp(logit - max) и множитель пересчёта накопленного; сам градиент по скрытому состоянию
   `sum_v exp(logit_v - max) W_v` копит в fp32 GEMM cuBLAS (`addmm`), домножая накопленное при
   росте максимума. После последнего куска `lm_head_finish_kernel` выдаёт loss, энтропию, accuracy и
   градиент. Метрики TRL/Soup и loss строк для rewind считаются в том же проходе. Строки промпта
   (~37% токенов) получают только энтропию и argmax: градиент через матрицу головы для них не
   считается. **Не побитно:** loss совпадает с вариантом "вес на GPU, один проход по словарю" до
   ~1e-7, но не побитно - GEMM кусками словаря суммирует в другом порядке, и у части логитов
   расходится 1 ulp fp16. Кривая loss и eval loss против базы от этого не изменились (тогда 0,01% / 0,04%).
9. **Веса слоёв в pinned-памяти CPU с момента загрузки** (`f041159`, `solution/hostload.py`).
   bitsandbytes квантует каждый `Linear4bit` на GPU как обычно (тот же код, те же значения), и
   сразу после этого упакованные NF4-байты и absmax копируются на хост, а копия на GPU
   освобождается; на GPU остаётся только маленькое состояние двойной квантизации. Для этого два
   патча transformers: `Bnb4bitQuantize.convert` после квантования переносит байты на хост, а
   `caching_allocator_warmup` не резервирует заранее GPU-память под веса, которые сразу уходят на
   хост; настройки аллокатора PyTorch не меняются (`expandable_segments` задаёт harness). `model.to()` из accelerate эти
   веса не трогает. `empty_cache()` после каждого из 196 весов не нужен: с `expandable_segments`
   следующий вес берёт освобождённую память, а лишние синхронизации стоили 0,34 с (`e32b8bd`).
   В шаге NF4-байты слоя копируются на GPU в один из двух слотов (`a123fba`; с тремя пик был на
   24 MiB выше весь прогон) по отдельному CUDA stream на слой
   вперёд (в backward - на слой назад), копия слоя (~23 MiB) идёт параллельно с GEMM. После
   обучения слоты освобождаются, а веса возвращаются на GPU только при первом forward-вызове
   4-битного слоя (сохранению LoRA-адаптера они не нужны).
10. **Эмбеддинг / `lm_head` в fp16 и на хосте** (`solution/offload.py`). peft не поднимает этот
   замороженный вес в fp32. Это без потерь: fp32-значения базы - точные копии fp16-чекпойнта, а
   `lm_head` база и так считает под autocast в fp16. Загрузчик кладёт этот вес сразу в память CPU
   (в карте устройств, которую читает загрузчик весов, только для эмбеддинга / `lm_head`), там он
   и остаётся весь прогон. Перед первым шагом эту память закрепляем на месте
   (`cudaHostRegister`, как в `torch.cuda._pin_memory_utils`), а не копируем в новый pinned-буфер:
   22 мс вместо 45 мс на одну копию 445 MiB, тот же указатель, те же асинхронные копии на GPU
   (`244d538`; если регистрация не удалась - прежняя копия). Когда вес возвращается на GPU
   (`restore_head`, откат), регистрация снимается. Строки эмбеддинга шага выбираются на CPU,
   копируются на GPU и приводятся к fp32 (побитно как у базы); голова стримится кусками (п. 8).
11. **Фоновая компиляция кернелов.**
    - Что: с момента `apply()` (имя модели - из того же `--config`, что читает Soup) поток того же
      процесса компилирует каждый вариант наших кернелов через те же функции, что и шаг обучения
      (ключи кэша Triton совпадают), и собирает их C-лаунчеры. Только компиляция, без запусков:
      модули CUDA грузятся на GPU в первом шаге, после пика загрузки модели (иначе +36 MiB к пику).
    - Как не мешать загрузке: поток один, стартует до импорта peft, работает с nice 19 (и его
      ptxas / gcc тоже), C-лаунчеры собираются с -O0; на 2 ядрах Kaggle каждый лишний поток тормозил
      загрузку сильнее, чем ускорял компиляцию.
    - Первой задачей поток закрепляет и сразу освобождает pinned-блоки того размера, который первый
      шаг попросит под NF4-веса (~645 MiB) и буфер входов слоёв: кэширующий host-аллокатор PyTorch
      отдаёт освобождённый блок тому же запросу (настройки аллокатора не меняются). До компиляции,
      а не после - так обучение не ждёт прогрев в начале (на Brev ожидание 0,45 -> 0,09 с, на Kaggle
      0,00 с); по стене на Kaggle это нейтрально (`3d06a30`).
    - Цифра: на T4 ~7-8 с компиляции идут в фоне, первый шаг - 0,6-1,0 с вместо 8,5 с. Seed'ы dropout
      объявлены `do_not_specialize`, иначе Triton перекомпилировал бы кернел при seed, кратном 16.
12. **Метрики TRL и строки rewind пишутся после backward** (хук `on_pre_optimizer_step`): их чтение на
   CPU больше не останавливает GPU между forward и backward; значения и порядок записей те же.
13. **Меньше запусков на шаг.** Один fp16-буфер весов LoRA на шаг вместо 8 приведений на слой, одна
    деквантизация на [q|k|v] и одна на [gate|up], первый слой без backward по входу, градиент по
    входу MLP через склеенный `[gate | up]` одним GEMM с K = 17 920 (split-K на 4 части мы сначала
    ввели, потом отменили - см. эксперименты).

### Как подключается и что остаётся прежним

`solution.apply()` ставит патчи:

- первым делом - рабочая область cuBLAS `:16:8` через `CUBLAS_WORKSPACE_CONFIG`, если пользователь
  её не задал (до первого вызова cuBLAS в процессе);
- `SFTTrainerWrapper.setup` - запуск фоновой компиляции, если она ещё не идёт;
- загрузка модели в transformers (`offload.py`, `hostload.py`) - эмбеддинг / `lm_head` сразу в
  память CPU, NF4-веса на хост сразу после квантования; только для Qwen2, которую bitsandbytes
  квантует в NF4 на одном GPU на fp16-пути Soup;
- `peft.prepare_model_for_kbit_training` - эмбеддинг Qwen2 остаётся в fp16;
- `SFTTrainerWrapper.train` - если модель распознана и это fp16-путь Soup на GPU sm_70+ (класс
  T4; условие ниже), подменяет `compute_loss` тренера и ставит стек потоков CUDA 16 байт. Новый
  `compute_loss` делает ту же бухгалтерию, что HF `Trainer` + TRL `SFTTrainer` + rewind-рекордер
  Soup: нормировка loss по `num_items_in_batch`, `entropy` по всем реальным токенам, `num_tokens`,
  `mean_token_accuracy` по токенам ответа, строки `rewind.jsonl` с loss каждой строки;
- патчи накладных расходов запуска (следующий раздел).

**Откат на код Soup** (`b2fdaac`). Всё, что слитый шаг не берёт, уходит в исходный `compute_loss`
без изменений: фейковые модули в тестах Soup, eval-режим, лишние ключи во входах, `label_smoother`,
другие архитектуры. Если откат случается уже после слитых шагов, 4-битные веса сначала
возвращаются на GPU. Если шаг не установился, а модель уже загружена с весами на хосте, перед
обучением кодом Soup все веса (NF4 и эмбеддинг) возвращаются на GPU (`hostload.restore`,
`offload.restore_embeddings`). Батч, который шаг не поддерживает (левый паддинг), отклоняется исключением
`UnsupportedBatch` до того, как шаг что-либо изменил, и тоже идёт в исходный код. Если наш шаг не
установился вообще, fp32-копия эмбеддинга восстанавливается и обучение идёт целиком кодом Soup.
Если не прошла самопроверка масок dropout (п. 2), каждый шаг сначала выгружает веса и голову,
затем поднимает `UnsupportedBatch` и возвращает веса на GPU для кода Soup - ~1,1 ГБ туда и обратно
на шаг: медленно, но корректно; во всех наших прогонах самопроверка проходила. Откат покрыт тестами
`solution/test_fallback.py`. В фиксированном конфиге кейса эти ветки не срабатывают, но
организаторы просят откат для неподдерживаемых входов
([t.me/souptasterschat/576](https://t.me/souptasterschat/576), п. 3).

**Только fp16-путь на GPU класса T4** (`20206f1`). Слитый шаг и фоновая компиляция включаются,
только если Soup обучает в fp16 (`fp16=True`, `bf16=False`) на GPU sm_70 или новее без bf16 - как
на T4. На GPU с bf16 (A100, L4, H100) Soup обучает в bf16, а наш шаг считает в fp16 и поменял бы
dtype вычислений, что запрещено ([t.me/souptasterschat/620](https://t.me/souptasterschat/620)). На
картах старше sm_70 (например, P100) Triton не работает. В обоих случаях идёт исходный код Soup, а
наши кернелы даже не компилируются.

Не меняются: модель, данные, батчи и их порядок, число шагов, LoRA (r, alpha, dropout 0,05,
целевые модули), оптимизатор и расписание lr, настройки тренера, выходы Soup, аллокатор.
Обучаемых параметров не добавляется: градиенты LoRA возвращает наш `autograd.Function`.

## Патчи накладных расходов запуска (не кернелы)

Замеряется вся команда `soup train`, поэтому кроме шага обучения мы убрали лишнюю работу самого
запуска и тренера HF на границе шагов. Организаторы подтвердили, что ускорение не обязано идти только от шагов обучения, и
попросили описать каждый такой патч ([t.me/souptasterschat/592](https://t.me/souptasterschat/592)).
Это работа на CPU: к доле наших кернелов (проверка 4) она не относится. Все патчи действуют только
внутри замеряемого запуска, ничего не сохраняют между запусками и ведут себя одинаково под замером
и в тестах (79 тестов Soup проходят с ними). Заглушек в `sys.modules` нет.

| Патч | Где | Что делает | Эффект на T4 |
|---|---|---|---|
| 1. Снимок `packages_distributions()` | `patch.py`, `patch_library_overheads` | повторные вызовы получают копию уже снятого словаря | -2,3 с |
| 2. bitsandbytes с `TORCHDYNAMO_DISABLE=1` только на время импорта | `startup.py`, `import_bitsandbytes` | bnb не тянет TorchInductor, который запуск не использует | -1,2 с |
| 3. Импорт без scikit-learn и (без `--wandb` / `--tracker`) без wandb | `startup.py`, `import_without_sklearn`, `import_without_wandb` | библиотеки, которые обучению не нужны, не импортируются | -1,05 с |
| 4. Фоновая компиляция не отнимает CPU у загрузки модели | `warmup.py`, `__init__.py` | nice 19, один поток компиляции с ранним стартом, лаунчеры с -O0 | nice: -0,6 с; один поток и ранний старт: -1,3 с; -O0: прогрев 8,7-9,7 -> 7,0-7,9 с |
| 5. Обходы модели на границе шага по спискам, снятым один раз (`f2fd8a2`, `9b65cde`) | `patch.py`, `_walk_model_once` | тренер HF не обходит ~1 000 модулей 4 раза за шаг | цикл 25,72 -> 25,12 с, вся команда -0,75 с (Brev) |
| 6. bf16 -> fp16 при загрузке модели - на GPU, а не на CPU (`777b83a`) | `patch.py`, `patch_weight_conversion` | конвертация чекпойнта идёт на GPU, биты те же | вне цикла 20,69 -> 19,34 с (Kaggle, 4 против 4) |

Подробно:

1. `importlib.metadata.packages_distributions()` обходит все установленные пакеты (~2,3 с на образе
   Kaggle). transformers вызывает её при импорте и хранит результат в
   `PACKAGE_DISTRIBUTION_MAPPING`, импорт trl вызывает её ещё раз. Мы отдаём каждому следующему
   вызывающему собственную копию словаря transformers: результат тот же (пакеты во время запуска не
   ставятся), а изменения одного вызывающего не видны другим - условие из
   [t.me/souptasterschat/592](https://t.me/souptasterschat/592); ещё раз подтверждено в
   [t.me/souptasterschat/5045](https://t.me/souptasterschat/5045) (п. 1).
2. bitsandbytes оборачивает несколько CPU-путей в `torch.compile` и при импорте тянет TorchInductor
   (~150 модулей); на CUDA у каждой операции bnb свой кернел. Переменная читается только при вызове
   `torch.compile`, сразу после импорта мы возвращаем её прежнее значение; путь обучения, harness и
   проверки не меняются. Разрешено: [t.me/souptasterschat/834](https://t.me/souptasterschat/834) (п. 4),
   прямо этот патч - [t.me/souptasterschat/5045](https://t.me/souptasterschat/5045) (п. 4).
3. transformers импортирует sklearn в двух модулях ради функций, которых обучение не использует
   (подбор порога assisted generation, GLUE-метрики); trl импортирует wandb в трёх модулях, даже
   если Soup ни во что не логирует. Пока импортируются ровно эти модули, проверка доступности
   отвечает "нет", затем восстанавливается. Библиотеки просто не импортируются, как на машине без них.
   Разрешено: sklearn - [t.me/souptasterschat/622](https://t.me/souptasterschat/622) (п. 1), wandb и
   другие ненужные импорты - [t.me/souptasterschat/2507](https://t.me/souptasterschat/2507) (п. 3), отложенные
   импорты без `sys.modules` - ещё раз [t.me/souptasterschat/5045](https://t.me/souptasterschat/5045) (п. 3); заглушек в `sys.modules`
   (запрещены, [t.me/souptasterschat/609](https://t.me/souptasterschat/609)) нет.
4. На Kaggle 2 ядра x 2 потока, и компиляция Triton (LLVM, ptxas, gcc) отнимала CPU у загрузки
   модели: с прогревом она шла 6,1 с, без него 3,0 с (GIL ни при чём: py-spy `--gil`).
   `os.setpriority` по native id потока: на Linux приоритет у каждого потока свой и наследуется
   ptxas / gcc. Компиляция идёт в одном потоке вместо трёх, зато стартует на ~1,5 с раньше (до
   импорта peft); отдельный поток только заводит страницы буфера `[gate | up]` (п. 4 "Что сделано").
   C-лаунчеры собираются через хук Triton `knobs.build.impl` с -O0 только пока идёт прогрев: это
   C-обвязка запуска наших кернелов, код кернелов (PTX / cubin) тот же.
5. Тренер HF на каждом шаге 4 раза обходит всю модель (~1 000 модулей, ~700 параметров):
   `num_parameters()` для счётчика FLOP, `model.parameters()` для клиппинга, `zero_grad()` и
   `model.train()`; в трейсе T4 это ~27 мс пустого GPU между шагами. Теперь обходы идут по спискам,
   снятым один раз при установке шага: те же параметры в том же порядке, тот же код HF / torch;
   исходный `train()` вызывается, только если какой-то модуль не в нужном режиме. `total_flos`,
   `grad_norm` и loss совпадают. Основание - по смыслу [t.me/souptasterschat/592](https://t.me/souptasterschat/592)
   (ускорения не только шагов обучения при тех же результатах).
6. transformers грузит каждый тензор чекпойнта через `tensor.to(cuda, fp16)`; из bf16-чекпойнта
   PyTorch сначала конвертирует его на CPU (~1,5-1,8 с на 2 ядрах Kaggle). Патч копирует тензор на
   GPU как есть кусками по 4M значений и конвертирует там: те же биты (все 338 тензоров чекпойнта),
   +8 MiB GPU на время куска, пик тот же. Только bf16 -> fp16 на CUDA, остальное - исходным кодом
   transformers. Основание - [t.me/souptasterschat/622](https://t.me/souptasterschat/622) (п. 1,
   ускорять подготовку до обучения можно); значения весов те же.

**Куда уходили ~21,7 с вне цикла** (Kaggle, код `b102d99`, до `777b83a`; py-spy по главному потоку,
секунды пересчитаны на прогон без профилировщика, x 0,83 - оценка):

## Как запустить

### Kaggle (как жюри)

1. Kaggle -> Create -> New Notebook -> File -> Import Notebook -> `templates/kaggle_notebook.ipynb`
   из этого репозитория. Или откройте наш сохранённый ноутбук (ссылка в начале) и нажмите Copy & Edit.
2. Справа: Accelerator **GPU T4 x2**, Internet **on** (нужен аккаунт с подтверждённым телефоном).
   Секреты не нужны, если репозиторий открыт; для закрытого шаблон берёт read-only токен из
   секрета Kaggle `GITHUB_TOKEN` (Add-ons -> Secrets). Необязательный секрет `HF_TOKEN` спасает от
   лимитов Hugging Face при скачивании модели.
3. В первой ячейке:
   ```python
   REPO_URL = "https://github.com/BAITC-Hacks/hack-fe30cb28-opus-5-5-ultracode.git"
   COMMIT = "[финал]"
   ```
4. Run All. Ноутбук ставит закреплённые версии пакетов, готовит данные, гоняет тесты `solution/`,
   затем `harness/run_task.py` (по одному запуску базы и решения) и `harness/check_rules.py`
   (проверка 10 - 79 тестов Soup). Итоговая таблица печатается в выводе, файлы -
   `runs/result.json` и `runs/checks.json`.
5. Замер как в таблице "Kaggle T4" (`--repeats 2`: база, решение, решение, база) - отдельной
   ячейкой в конце ноутбука:
   ```
   !cd /kaggle/working/repo && python harness/run_task.py --repeats 2 --out runs_r2 && python harness/check_rules.py --result runs_r2/result.json
   ```
   В нашем сохранённом ноутбуке (ссылка в начале) это последняя ячейка, ровно в таком виде; из неё
   таблица "Kaggle T4" выше.

Больше ничего делать не нужно: решение подключается через `solution.apply()`, ручных правок и
переменных окружения нет. В нашем сохранённом ноутбуке можно сверить вывод с таблицей выше.

### Локально (Linux + NVIDIA T4, или другой GPU для тестов)

Официальный замер - на образе Kaggle из шаблонного ноутбука: Python 3.13, torch 2.11.0+cu128,
triton 3.6.0, datasets 4.8.5 уже стоят в образе, ноутбук доставляет только пакеты Soup (версии из
`result.json` нашего Kaggle-прогона). Локальная установка должна повторять эти версии: без явного
закрепления pip сейчас ставит torch 2.15.0 + triton 3.9.0 (CUDA 13). Решение работает и там (чистый
клон и свежий venv на Brev T4, `b102d99`: тесты `solution/`, 79 тестов Soup, все 10 проверок,
1,581x / 17,66x, eval -0,009%), но засчитывается замер на версиях Kaggle. Весь путь из этого
README проверен на финальном `5f9b2ef` с нуля: чистый клон, свежие venv, кэш pip, `HF_HOME` (модель
и данные скачаны анонимно) и кэш Triton, команды ниже и ячейки шаблонного ноутбука дословно.
Ставятся ровно 2.11.0+cu128 / 3.6.0, `pip check` чистый, `pytest solution` - 60 passed, 79 тестов
Soup passed, все 10 проверок в каждом замере (Brev T4: `run_task.py --repeats 2` 1,365x / 24,03x,
шаблон r1 1,397x / 24,03x, ячейка r2 1,406x / 23,95x, пик 597-599 MiB, eval -0,001..+0,002%,
кривая loss в среднем 0,01%; время на Brev с Kaggle не сравнивается). Самый первый замер в только что созданном окружении на Brev

Повторять замер нужно на T4. **На Ampere и новее (RTX 30xx/40xx, A100, L4, H100) слитый шаг
сам не включается, так и задумано** (`20206f1`): Soup там обучает в bf16, и в логе решения будет
`[solution] not the fp16 training path of a T4-class GPU ...: training with the original code path`.
Это не поломка - обучение идёт исходным кодом Soup, со временем и памятью базы. Тесты `solution/`
и 79 тестов Soup на таких GPU проходят: они не зависят от пути обучения (проверено на RTX 4060
после `20206f1`).

Чтобы посмотреть сам слитый шаг на bf16-GPU, Soup нужно принудительно перевести на его fp16-путь,
как на T4. Мы делали это обёрткой только для локальной отладки (в решение она не входит):

### Регуляторы (`solution/patch.py`)

| Регулятор | По умолчанию | Что делает |
|---|---|---|
| `OFFLOAD_HEAD` | `True` | эмбеддинг / `lm_head` весь прогон в pinned-памяти CPU, голова кусками словаря; `False` - вес на GPU (пик выше на ~420 MiB - на `2da275a` 1 233 против 813; loss побитно как у прохода по всему словарю) |
| `HOST_NF4_AT_LOAD` | `True` | NF4-веса на хост сразу после квантования при загрузке модели |
| `OFFLOAD_WEIGHTS` | `True` | подкачка NF4-весов из pinned-памяти CPU в шаге; `False` - веса на GPU, только вместе с `HOST_NF4_AT_LOAD = False` (до выгрузок при загрузке пик был 1 761 MiB против 1 385, цикл тот же) |
| `OFFLOAD_ACTIVATIONS` | `True` | входы слоёв для backward в pinned-памяти CPU (`InputStream`); `False` - на GPU (loss и градиенты побитно те же, пик выше) |
| `OFFLOAD_GU` | `True` | выходы `[gate \| up]` в pinned-памяти CPU вместо пересчёта в backward (`GuStream`); `False` - пересчёт (loss и градиенты побитно те же на шагах с кольцом целых выходов; на Kaggle медленнее на ~2 с, на машине с медленной шиной, как Brev, быстрее на ~5 с) |
| `OFFLOAD_ATTN` | `True` | q, k/v, выход attention и `o_proj` слоёв с `[gate \| up]` в pinned-памяти CPU вместо пересчёта attention в backward (`AttnStream`); `False` - пересчёт (loss и градиенты побитно те же) |
| `ATTN_MIN_GBPS` | 9,0 | `AttnStream` включается, только если копия host -> GPU, измеренная на первом шаге, не медленнее этого (ГБ/с); Kaggle 10,1-12,3, Brev 6,3; 0 - включать всегда |
| `CUBLAS_WORKSPACE` (`solution/startup.py`) | `":16:8"` | рабочая область cuBLAS на handle, если `CUBLAS_WORKSPACE_CONFIG` не задан пользователем; `None` - значение PyTorch по умолчанию (4 MiB x 2 + 16 KiB x 8) |

### Тесты корректности

- `solution/test_kernels.py`: каждый кернел против PyTorch, forward и backward; NF4-деквантизация
  побитно против `bitsandbytes`, в том числе на весе полного размера; varlen attention против SDPA
  по каждой строке; **весь шаг против HF + PEFT под fp16 autocast** на маленькой 4-битной Qwen2
  (измерено: loss до 2e-6, градиенты LoRA до 0,1-0,5% - уровень шума fp16; тест требует loss
  < 2e-3 и градиенты < 2e-2 относительно); стриминг весов, хранение
  gate/up и полное хранение дают побитно те же loss и градиенты, экономный шаг - те же с точностью
  до разбиения GEMM на куски; `restore` возвращает веса побитно; маска dropout кернела против
  `F.dropout` PyTorch бит в бит на 5 формах (`test_dropout_masks_are_torchs`), весь шаг с dropout
  против HF + PEFT (`test_fused_step_dropout_matches_hf`), самопроверка первого шага и откат при
  несовпадении (`test_dropout_self_check`).
- `solution/test_fallback.py`: откат на код Soup в eval-режиме, с лишним ключом во входах, при
  левом паддинге и в цепочке train - eval - train после слитых шагов.
- `solution/test_hostload.py`: NF4-веса, выгруженные на хост при загрузке, - те же значения, тот же
  слитый шаг, и исходный путь Soup после `restore()`.
- `solution/test_host_head.py`: голова кусками с хоста против головы с весом на GPU, весь шаг с обеими
  выгрузками.
- После загрузки с весами и эмбеддингом на хосте: откат на код Soup и обратно; весь слитый шаг с
  весами и головой, которые стримятся с хоста, против HF + PEFT, в том числе на батче из одной
  строки в 4 токена (`6863f52`).
- `solution/test_host_head.py::test_layer_inputs_in_host_memory_are_exact`: входы слоёв на хосте
  (`InputStream`) - loss и градиенты LoRA побитно как с входами на GPU, на 2 и 7 слоях, с кольцом
  из 1, 2 и 3 слотов (слоты переписываются и подкачиваются заранее) и на двух шагах подряд.
- `solution/test_host_head.py::test_host_head_pins_embedding_in_place`: эмбеддинг закрепляется на
  месте (тот же указатель) и после возврата на GPU побитно тот же, регистрация снята.
- `solution/test_host_head.py::test_ce_kernels_take_the_target_logit_before_the_row_is_overwritten`:
  оба кернела головы 10 раз подряд на 1 024 строках, loss каждого токена совпадает с
  logsumexp - logit до 1e-3 (ловит гонку, описанную ниже).
- `solution/test_host_head.py::test_gate_up_in_host_memory_is_exact`: `[gate | up]` на хосте вместо
  пересчёта - loss и градиенты LoRA побитно как с пересчётом, с весами, головой и входами слоёв на
  хосте, на двух шагах подряд; на 2 и 7 слоях, кольцо из 1 и 2 слотов, часть слоёв держит
  `[gate | up]` на GPU.
- `solution/test_host_head.py::test_long_step_gate_up_in_host_memory_in_chunks`: длинный шаг с
  `[gate | up]` на хосте кусками - loss и градиенты побитно как у кускового MLP экономного шага.
- `solution/test_host_head.py::test_attention_in_host_memory_is_exact`: тензоры attention на хосте
  (`AttnStream`) - loss и градиенты LoRA побитно как с пересчётом attention, на 2 и 7 слоях, с
  весами, головой, входами и `[gate | up]` на хосте, в том числе со слоями, держащими `[gate | up]`
  на GPU; `test_attention_ring_only_beside_whole_gate_up_ring` - кольцо не берётся на шаге с
  кусками `[gate | up]`, на экономном шаге и на границе, где помещается только кольцо
  `[gate | up]`; `test_long_step_attention_in_host_memory_is_exact` - длинный шаг, который берёт
  `AttnStream` по `_held_peak`, побитно как без него.
- `solution/test_host_head.py::test_cuda_stack_limit_leaves_the_kernels_alone`: со стеком потоков
  CUDA 16 байт лимит держится, а cuBLAS, attention и `lm_head_ce_kernel` дают те же значения.
- 79 тестов Soup с нашими патчами (`SOUP_APPLY_SOLUTION=1`).

Всего в `solution/` 70 тестов (с параметрами; `pytest --collect-only`); в ноутбуке на Kaggle на
финальном коммите - [финал]. Пороги fp16 подобраны под T4, где два теста раньше падали только на
этой карте (`42c35e5`, `af4857b`).

**Гонка в кернелах головы - нашли своим аудитом прогонов и исправили** (`a9a1c25`).
- Что нашли: сравнив loss строк rewind между двумя запусками решения на одних и тех же батчах во
  всех 428 прогонах, - 13 случаев, где у одного токена на случайном шаге loss больше на 9,4-22,6.
- Причина: `lm_head_piece_kernel` и `lm_head_ce_kernel` читали логит целевого токена из строки уже
  после того, как другие warp'ы той же программы могли записать туда градиент; барьера не было.
- Влияние: только записанный loss шага (+2-4% на этом шаге) и строка `rewind.jsonl`; градиенты,
  энтропия и accuracy были верны. Проверка 6 упала бы, только если ошибка пришлась на первый шаг
  (~0,05% прогонов); в засчитываемых Kaggle-прогонах её не было.
- Исправление: логит цели берётся в первом проходе по строке, до любой записи, значение то же. Стресс
  на T4 (1 600 запусков по 1 024 строки): 2 неверных токена до, 0 после; тест выше.

## Ограничения и что не получилось

- **Решение заточено под этот кейс:** Qwen2 (RoPE `default`, без sliding window), веса NF4 из
  bitsandbytes, LoRA только на `q_proj`/`v_proj`, fp16-путь Soup на GPU sm_70+ без bf16 (T4).
  Всё остальное идёт исходным кодом Soup без ускорения - корректно, но медленно. В том числе на
  bf16-GPU (A100, L4, H100) решение не ускоряет ничего: Soup там обучает в bf16, а наш шаг
  считает в fp16, и сменить dtype вычислений нельзя
  ([t.me/souptasterschat/620](https://t.me/souptasterschat/620)). bf16-вариант шага мы не делали.
- **Скорость - наша слабая сторона.** GEMM cuBLAS занимают ~69% работы GPU в шаге и уже на потолке
  T4; свой GEMM на Triton для sm_75 без тензорных ядер не получился (см. эксперименты). Пересчёт
  слоя (qkv, o, attention, нормы - GEMM `[gate | up]` теперь не пересчитывается) ещё стоит часть
  цикла: мы сознательно платим им за ~6x меньше памяти активаций.
- **Вне цикла обучения мы выигрываем мало.** Импорты, загрузка модели, сохранение и выход - почти
  те же, что у базы; патчи запуска дают ~-8,5 с (сумма A/B отдельных патчей), а фоновая компиляция даже с nice 19 в одном потоке
  ещё отнимает ~1 с у загрузки модели (2 ядра x 2 потока). Остальное - не наше и есть у базы:
  `packages_distributions()` внутри `import transformers` в харнессе до `apply()` (2,3 с), ленивая загрузка ~78
  модулей CUDA кернелов PyTorch в первом шаге (~0,4 с) и завершение интерпретатора (~1,7 с, у базы
  1,72 с). На машинах с быстрым CPU (Brev) время вне цикла у нас и у базы почти одинаковое.
- **Ниже ~461 MiB пик не опускается.** ~113-115 MiB - вне аллокатора PyTorch: контекст CUDA ~65
  (уже со стеком 16 байт), модуль `Copy.cu` кастов PyTorch +16, cuBLAS и attention +12, остальное -
  наши кернелы. Остальные лимиты контекста (буфер printf, куча `malloc` на устройстве и др.)
  резервируются лениво - их уменьшение даёт 0; выгрузить модули нельзя - кернелы нужны шагу;
  рабочую область cuBLAS мы уже уменьшили до `:16:8` (`c4b156e`, -20 MiB). Резерв аллокатора - 346
  MiB: большой пул 300 при allocated 250-265 (фрагментация, сегменты по 20 MiB) и малый 46 (шаг
  AdamW по LoRA); настройки аллокатора харнесса менять нельзя
  ([t.me/souptasterschat/4060](https://t.me/souptasterschat/4060)), а потолок шага ниже 340 пик
  уже не опускает (на Brev 320 / 300 - те же 461), только переводит длинные шаги в экономный путь.
- **Выгрузки зависят от шины.** Каждый шаг гоняет по PCIe голову (445 MiB), входы слоёв (~135 MiB в
  каждую сторону на батче в 820 токенов) и `[gate | up]` (~560 MiB в каждую сторону на публичных
  строках). На Kaggle это в пределах разброса запусков, а `[gate | up]` на хосте даже быстрее
  пересчёта; на Brev с вдвое более медленной шиной - ~2,4 с, ~0,7 с и ~5 с (цифры - в экспериментах).
  На такой машине `OFFLOAD_GU = False` вернёт пересчёт. Тензоры attention (`AttnStream`, ~10 KiB на
  токен и слой в каждую сторону) решение само держит на хосте только при шине от 9 ГБ/с, иначе
  пересчитывает: на Brev они стоили +4 с.
- **Память хоста.** Pinned-память на хосте: NF4-веса (~645 MiB), эмбеддинг / `lm_head` (445 MiB),
  буфер входов слоёв (под 4 x 512 токенов - 336 MiB, pinned-аллокатор PyTorch округляет до 512 MiB)
  буфер `[gate | up]` (1,9 ГиБ под 2 048 токенов) и буфер тензоров attention (560 MiB под 2 048
  токенов), всего ~4,2 ГБ. Отдельного лимита на ОЗУ и
  pinned-память в ТЗ нет ([t.me/souptasterschat/2103](https://t.me/souptasterschat/2103), п. 3), на Kaggle
  (~30 ГБ ОЗУ) это немного, но на машине с маленьким ОЗУ это стоит учитывать.
- **Длинные батчи медленнее.** Экономный шаг удерживает пик, но на самых длинных батчах
  пересчитывает attention дважды: на стресс-срезе из одних таких батчей цикл +9% (замер до
  `6b1cc09`).
- **Speedup шумит между инстансами T4** (база 79-97 с на Kaggle, 63-75 с на Brev), поэтому
  speedup одной сессии нельзя переносить на другую; память стабильна. На Kaggle T4 всё время
  нагрузки упирается в предел мощности 70 Вт, частота падает с нагревом, и стена решения в одной
  сессии гуляет на ±2% (раздел "Kaggle T4").
- **Энтропия и loss строк считаются в fp32** (в базе часть этих величин округляется до fp16):
  расхождение с базой - сотые доли процента, в допусках проверки 5.
- **Loss не побитно равен варианту без выгрузки головы:** GEMM головы кусками словаря суммирует в
  другом порядке (1 ulp fp16 у части логитов, loss до ~1e-7). Против базы все проверки проходят.
- **Что не успели:** GEMM на тензорных ядрах T4 через PTX `mma.sync` внутри Triton (вопрос
  организаторам [t.me/souptasterschat/496](https://t.me/souptasterschat/496) остался без ответа) - главный оставшийся рычаг скорости; bf16-вариант шага для
  Ampere и новее.

## Структура

| Путь | Что |
|---|---|
| `solution/__init__.py` | `apply()`: порядок патчей и старт фоновой компиляции |
| `solution/kernels.py` | все наши `@triton.jit` кернелы |
| `solution/engine.py` | слитый шаг (`FusedQwen2`): упаковка батча, `_Layer`, `NF4Weight` / `NF4Group`, `HostHead` / `_HostHead` (голова кусками с хоста; `_Head` - запасной путь с весом на GPU), `WeightStream` (веса слоёв с хоста), `_HostRing` / `InputStream` / `GuStream` / `AttnStream` (входы слоёв, `[gate \| up]` и тензоры attention на хосте), `TorchDropout` (маски dropout базы), прогноз пика |
| `solution/hostload.py` | NF4-веса на хост сразу после квантования при загрузке модели |
| `solution/offload.py` | эмбеддинг / `lm_head` в память CPU при загрузке модели |
| `solution/patch.py` | подключение к Soup, бухгалтерия метрик, откат, `patch_prepare_kbit` (эмбеддинг в fp16), патч `packages_distributions`, `patch_weight_conversion`, `set_cuda_stack`, обходы модели на границе шага, замер шины для `AttnStream` (`_h2d_gbps`) |
| `solution/startup.py` | рабочая область cuBLAS `:16:8`; патчи импорта: bitsandbytes без TorchInductor, без sklearn / wandb |
| `solution/warmup.py` | фоновая компиляция кернелов (один поток, nice 19, лаунчеры с -O0), заранее закреплённые блоки и заведение страниц буфера `[gate \| up]` |
| `solution/test_*.py` | тесты корректности, отката и обеих выгрузок |
| `dev/mask_probe/` | отладочный зонд: маски dropout решения против масок базы на настоящей модели |
| `presentation/` | слайды (`make_slides.py` -> `slides.pdf`) |
| `harness/`, `tests/`, `task/`, `templates/` | без изменений, из шаблона |
