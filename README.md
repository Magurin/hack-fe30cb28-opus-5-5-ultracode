# Soup Kernel Challenge: слитый шаг обучения Qwen2 + NF4 + LoRA на своих Triton-кернелах

Решение кейса Soup на Decentrathon 6.0. Команда `soup train` (Soup 0.77.0,
Qwen2.5-1.5B-Instruct в NF4, LoRA r=16 на `q_proj`/`v_proj`, batch 4, 64 шага, Kaggle T4, fp16)
обучает **тот же адаптер на тех же батчах**, но шаг обучения пересобран вокруг наших
Triton-кернелов: без паддинга, без fp32-копий активаций, без логитов на весь словарь, с пересчётом
слоя в backward. Замороженные веса на GPU не живут: NF4-веса слоёв и общий эмбеддинг / `lm_head`
с момента загрузки модели лежат в pinned-памяти CPU и подкачиваются на GPU по мере надобности.

## Архитектура за 5 минут

`solution.apply()` вызывается harness до сборки модели. Он ставит патчи (`solution/patch.py`), и
в начале `SFTTrainerWrapper.train` подменяет `compute_loss` тренера на наш слитый шаг
(`solution/engine.py`), если модель распознана (Qwen2 + bitsandbytes NF4 + LoRA на q/v) и Soup
обучает в fp16 на GPU класса T4. Тренер HF,
оптимизатор, GradScaler, расписание lr, логирование и выходы Soup остаются своими.

Загрузка модели (до первого шага):

```
transformers / bitsandbytes грузят Qwen2 как обычно, но
  эмбеддинг / lm_head (fp16, 445 MiB)  -> сразу в память CPU (offload.py), на GPU не попадает
  каждый Linear4bit: квантуется в NF4 на GPU тем же кодом bnb -> упакованные байты и absmax
                     сразу копируются на хост, копия на GPU освобождается (hostload.py)
итог: на GPU только нормы, LoRA и маленькое состояние двойной квантизации
```

Один шаг обучения:

```
батч 4 x L с паддингом справа
  -> упаковка: N реальных токенов подряд + cu_seqlens (паддинга нет, строки не смешиваются)
  -> эмбеддинг: строки берутся из fp16-таблицы на CPU, копируются на GPU -> fp32 residual
  -> 28 x _Layer (autograd.Function; для backward хранит только свой вход, 6 KiB на токен)
       WeightStream: NF4-байты следующего слоя едут с хоста на GPU по отдельному CUDA stream
       nf4_dequant  [q|k|v], o, [gate|up], down  -> fp16
       rms_fwd      residual add + RMSNorm + входы LoRA с dropout
       GEMM qkv (cuBLAS) -> qkv_rope_fwd (LoRA-дельты + RoPE) -> varlen attention (PyTorch, cu_seqlens)
       GEMM o -> rms_fwd -> GEMM [gate|up] -> glu_fwd (SwiGLU) -> GEMM down
  -> голова (HostHead): lm_head едет с хоста кусками по 8 192 строки словаря (3 буфера по 24 MiB),
       копии начинаются ещё на последних слоях forward; на каждый кусок:
       GEMM lm_head (cuBLAS) -> lm_head_piece (online logsumexp, энтропия, argmax, накопление
       градиента по скрытому состоянию); в конце lm_head_finish: loss, метрики, градиент.
       Логиты на весь словарь не существуют ни в какой момент
backward, слой 27 -> 0:
  веса подкачиваются в обратном порядке, forward слоя пересчитывается
  (полностью, частично или "экономно" - решает прогноз пика шага, см. ниже),
  дальше *_bwd-кернелы и GEMM cuBLAS; градиенты LoRA возвращает наш autograd.Function
```

Четыре решения, из которых всё следует:

1. **Заменяем весь шаг, а не отдельные модули HF.** Память базы съедают не веса, а то, что модули
   HF хранят между собой: fp32-выходы проекций bitsandbytes, полные логиты TRL, паддинг. Убрать это
   можно только на уровне всего шага.
2. **Математика базы сохраняется.** Округления до fp16 в тех же местах (выходы проекций, вход
   attention, произведение в MLP), fp32 для residual, норм, RoPE, softmax и loss. Отсюда кривая loss
   в пределах 0,01-0,05% от базы.
3. **GEMM остаются в cuBLAS, всё между ними - наши кернелы.** На T4 (sm_75) `tl.dot` в Triton 3.6 не
   использует тензорные ядра (~1 TFLOPS против 16-34 у cuBLAS, замер), поэтому свой GEMM - проигрыш.
   Выигрыш - в слиянии поэлементных операций и приведений dtype, которые в базе занимают ~44% профиля.
4. **Замороженное - на CPU, на GPU только то, что считается сейчас.** NF4-веса (~650 MiB) и
   эмбеддинг / `lm_head` (445 MiB) уходят на хост ещё при загрузке модели, а на GPU приезжают кусками
   на время своего GEMM. Шаг сам прогнозирует свой пик и держится под потолком памяти, а запас под
   ним тратит на хранение активаций вместо пересчёта.

### Наши Triton-кернелы (`solution/kernels.py`)

Доля - время кернела (CUDA events harness) от времени обучения, шаги 3-64; прогон коммита `5c93f07`
на Brev T4, публичные строки. Ни один кернел не использует `tl.dot`.

| Кернел | Что сливает (что заменяет в базе) | Доля |
|---|---|---|
| `nf4_dequant_kernel` | NF4 + двойная квантизация absmax -> fp16 за один проход, побитно как `bitsandbytes.functional.dequantize_4bit` (у bnb - 2 кернела); один запуск на [q\|k\|v] и один на [gate\|up] | 8,0% |
| `rms_fwd_kernel` | residual add + RMSNorm в fp32 -> fp16 + входы обеих LoRA с dropout (маска - функция seed и позиции, не хранится); в базе 5-6 операций PyTorch и касты | 2,4% |
| `rms_bwd_kernel` | backward RMSNorm, сумма градиентов основной ветки и обеих LoRA (маски регенерируются), residual-градиент | 1,2% |
| `qkv_rope_fwd_kernel` | разрезка qkv одного GEMM, LoRA-дельты, RoPE -> q, k, v в раскладке attention; k/v сразу расширены под GQA | 1,0% |
| `qkv_rope_bwd_kernel` | обратный поворот, сумма градиентов по группам GQA, сборка `[dq \| dk \| dv]` под один GEMM | 0,4% |
| `glu_fwd_kernel` | SwiGLU над слитым выходом `[gate \| up]` одного GEMM (в базе - fp32 silu * up) | 1,3% |
| `glu_bwd_kernel` | backward SwiGLU на месте в `[dg \| du]` под один GEMM | 2,2% |
| `lm_head_piece_kernel` | голова по кускам словаря: online-состояние каждой строки (максимум, сумма exp, сумма exp * logit, лучший логит и его индекс) переносится от куска к куску; для строк с целевым токеном пишет exp(logit - max) под GEMM градиента и множитель пересчёта накопленного; вынимает строку веса целевого токена. Заменяет fp32-логиты, cross-entropy, entropy и accuracy TRL, loss строк для rewind | 0,55% |
| `lm_head_finish_kernel` | после последнего куска: loss, энтропия, accuracy и градиент по скрытому состоянию `acc / s - W_target` в fp16 | 0,01% |
| `lm_head_ce_kernel` | та же голова за один проход по всему словарю, когда вес `lm_head` на GPU (`OFFLOAD_HEAD = False`); блоки и операции у `lm_head_piece_kernel` те же, поэтому при тех же логитах loss, энтропия и accuracy совпадают побитно | - |
| **Вместе** | проверка 4 требует >= 5% | **17,1%** |

Пример из шаблона (`swiglu.py`) удалён: наши GLU-кернелы работают над другим (слитым) layout и по
метрике `check_rules.py` похожи на пример на 0,65-0,70 (порог ручной проверки 0,8).

### Источники идей (код написан нами)

- Fused RMSNorm и chunked "fused linear cross-entropy": [Liger-Kernel](https://github.com/linkedin/Liger-Kernel),
  [Unsloth](https://github.com/unslothai/unsloth), [Cut Cross-Entropy (Wijmans et al., 2024)](https://arxiv.org/abs/2411.09009).
- Online softmax / logsumexp: Milakov, Gimelshein, [arXiv:1805.02867](https://arxiv.org/abs/1805.02867).
- NF4 и двойная квантизация: QLoRA, Dettmers et al., [arXiv:2305.14314](https://arxiv.org/abs/2305.14314), формат `bitsandbytes`.
- Пересчёт активаций: Chen et al., [arXiv:1604.06174](https://arxiv.org/abs/1604.06174).
- Подкачка весов с хоста, в том числе головы кусками словаря: ZeRO-Offload / ZeRO-Infinity ([arXiv:2101.06840](https://arxiv.org/abs/2101.06840)).
- Attention без паддинга: FlashAttention varlen API ([arXiv:2205.14135](https://arxiv.org/abs/2205.14135));
  у нас - встроенное в PyTorch ядро `_efficient_attention_forward/backward` с `cu_seqlens`.

## Откуда 17x по памяти

Авторы кейса ожидали от сильных команд 1,5-2x по памяти, поэтому разберём, откуда 17x. Пик
nvidia-smi базы на T4 - 14 345 MiB, из них 13 373 MiB - тензоры PyTorch (allocated). Что держит
память в базе (разбор кода, 4 строки до 512 токенов):

| Что держит память в базе | Порядок величины |
|---|---|
| Активации 28 слоёв для backward, в основном fp32: выходы gate/up MLP `(токены x 8960)` в fp32 (bnb `Linear4bit` возвращает fp32), их silu и произведение, fp32-нормы, fp32-RoPE | ~9-10 ГБ |
| Логиты `(4, T, 151936)`: fp16, fp32-копия в loss, log_softmax, градиент, копия для accuracy | ~3-4 ГБ |
| Модель: NF4-веса ~650 MiB + эмбеддинг/`lm_head`, поднятый peft в fp32, 933 MiB | ~1,6 ГБ |

Водопад: что убирает каждый шаг.

| Шаг | Пик | Где измерено |
|---|---|---|
| База | 13 373 MiB allocated, **14 345** nvidia-smi | T4 |
| Слитый шаг: без паддинга, активации в fp16, логиты кусками по 256 строк | 3 355 MiB allocated | RTX 4060, fp16-путь T4 |
| + пересчёт слоя в backward (храним только вход слоя, 6 KiB/токен) | 1 468 MiB allocated | RTX 4060 |
| + эмбеддинг остаётся в fp16 (peft не поднимает его в fp32) | пик подготовки модели 3 158 -> 1 150 MiB reserved | RTX 4060 |
| + NF4-веса слоёв в pinned-памяти CPU, 3 слота на GPU | 1 385 nvidia-smi (без стриминга - 1 761) | T4 |
| + слоты выделяются после освобождения весов, ленивый возврат весов после обучения | 1 275 nvidia-smi | T4 |
| + экономный шаг для самых длинных батчей | 1 275 и на длинных срезах (стресс 4 x 512: 1 293 вместо 1 393) | Brev T4 |
| + NF4-веса уходят на хост сразу после квантования, ещё во время загрузки (`f041159`) | пик загрузки 1 277 -> ~603; пик запуска 1 233, его теперь задаёт обучение | Brev T4 |
| + эмбеддинг / `lm_head` весь прогон в pinned-памяти CPU, голова кусками словаря (`5c93f07`) | **813** nvidia-smi (стресс 4 x 512: 873) | Brev T4 |

Итог: allocated 588,8 MiB, reserved 648 MiB, nvidia-smi **813 MiB**. Оставшиеся ~165 MiB вне
аллокатора PyTorch - это CUDA-контекст, модули наших кернелов и cuBLAS. На GPU больше нет ни одного
замороженного веса целиком: только нормы, LoRA, состояние двойной квантизации, три слота весов
слоя, три буфера кусков головы и активации шага. Пик теперь всегда приходится на обучение, и его
держит потолок шага (см. ниже). Для сравнения: ТЗ приводит Unsloth на ~6x (2,3-2,4 ГБ), так что 17x -
это "дальше Unsloth" за счёт подкачки весов и пересчёта, а не артефакт замера: проверка 9 сверяет
пик nvidia-smi со счётчиками PyTorch внутри процесса.

**Потолок шага.** Раньше потолок задавала загрузка модели: шаг тратил на хранение активаций всё,
что было под её пиком. Теперь веса на GPU при загрузке не лежат, и потолок считается так, будто
NF4-веса загрузились на GPU (пик загрузки + их байты - 112 MiB запаса): шаги сохраняют тот же запас
под хранение, что и раньше, а освобождённые эмбеддингом 445 MiB целиком идут в экономию памяти.
Регулятор `STEP_CAP_MIB` в `solution/patch.py` задаёт потолок явно.

**Почему "максимум памяти", а не "освобождённое - на скорость".** Баллы: скорость
35 x ln s / ln s_лучш, память 30 x ln m / ln m_лучш (ТЗ, 11.2). Можно было держать пик ~1 233 MiB и
отдать 445 MiB шагам под хранение активаций, но на T4 это мало ускоряет: кривая `EXTRA_MEMORY_MIB`
на текущем коде даёт -1,8 с за +512 MiB (m 11,25 -> 8,28) и -2,9 с за +1 024 MiB. Цена выгрузки
головы по времени на Kaggle - ноль в пределах шума: A/B в одной сессии, цикл 27,9-28,1 с против
28,2 с, вся команда 49,5-50,1 против 50,0 с. Поэтому на Kaggle выгрузка головы - чистый выигрыш по
памяти (m 11,6 -> 17,6) при той же скорости:

| Сценарий у лучших конкурентов | Без выгрузки головы (m 11,6) | С выгрузкой (m 17,6) |
|---|---|---|
| по памяти лучше нас никого (m < 11,6) | память 30 | память 30, при равной сумме баллов выше команда с лучшей памятью (ТЗ, 11.2) |
| у кого-то m = 15 | память 27,2 | память 30 (+2,8) |
| у кого-то m = 17 | память 26,0 | память 30 (+4,0) |

Риск: если у машины жюри PCIe медленный, как у Brev (~6,3 ГБ/с), выгрузка головы стоит ~2,4 с
(s 1,65 -> 1,56 на Brev), то есть ~2,5 балла за скорость при лидере s = 2,2. Ноутбук жюри - Kaggle,
где мы меряли ~13 ГБ/с и разницы не видим, поэтому этот риск мы приняли.

## Что сделано и почему

Разбор базового пути на T4 (fp16, без bf16) показал, откуда 14 ГБ и ~44% поэлементных операций в
профиле:

1. `prepare_model_for_kbit_training` поднимает всё не-4-битное в fp32, включая общий эмбеддинг /
   `lm_head` (151 936 x 1 536) - весь residual stream идёт в fp32;
2. `bitsandbytes.nn.Linear4bit` приводит выход каждой проекции обратно к fp32, поэтому выходы
   gate/up MLP (токены x 8 960) хранятся для backward в fp32;
3. батч дополняется паддингом до самой длинной строки: при ~205 реальных токенах на строку и
   ~380 по длине батча почти половина работы идёт на pad-токены;
4. логиты `(4, T, 151 936)` существуют в fp16, в fp32 для loss, в виде градиента и копии для
   accuracy - несколько гигабайт на пике.

Что мы с этим сделали:

1. **Удаление паддинга внутри батча.** Строки батча упаковываются в одну последовательность из N
   реальных токенов, attention считается varlen-causal по `cu_seqlens` встроенным в PyTorch
   memory-efficient ядром (то же семейство, что SDPA в базе). Батчи и их порядок не меняются, строки
   разных батчей не смешиваются, `num_tokens` = сумма `attention_mask`.
2. **Слой декодера = один `torch.autograd.Function`**, который хранит для backward только свой вход
   (fp32 residual, 6 KiB на токен) и пересчитывает forward в backward с теми же seed'ами dropout.
   Это ~6x меньше памяти активаций за лишний проход GEMM qkv, o и gate/up (деквантизованные веса в
   backward нужны всё равно). Градиент `down_proj` считается до пересчёта, поэтому слой не держит
   все четыре распакованных веса сразу (-27,5 MiB на пике).
3. **Адаптивный пересчёт.** В начале шага прогнозируем его пик по уже выделенной памяти и числу
   токенов N (модель из размерностей сети; сверена с замером по всем шагам: реальный пик - 65 MiB +
   218 KiB на токен над началом шага, прогноз держится на 46 MiB + 14 KiB/токен выше). В запас под
   потолком шага (минус 112 MiB на фрагментацию аллокатора и модули CUDA, подгружаемые во время
   обучения; как считается потолок - в разделе про память) кладём выход GEMM `[gate | up]` последних k слоёв - для них самый тяжёлый GEMM
   пересчёта не повторяется. Если на коротком батче gate/up уже хранится у всех слоёв, остаток идёт
   на остальные промежуточные тензоры (такие слои не пересчитывают ничего). На T4 цикл стал на
   14-20% быстрее, пик не изменился. Регулятор `EXTRA_MEMORY_MIB` в `solution/patch.py` позволяет
   шагам занимать память сверх потолка (кривая - в экспериментах), по умолчанию 0.
4. **Экономный шаг для самых длинных батчей** (`fbe7502`). Если даже без хранения шаг выше
   потолка (у нас это ~1 870+ токенов в батче, ~5% случайных срезов), пересчёт идёт в две части:
   сначала до входа MLP, после backward MLP - attention ещё раз для своего backward; MLP считается
   кусками по 512 токенов, так что `[gate | up]` живёт кусками. На батче 4 x 512 пик шага над его
   началом 570 -> 477 MiB, allocated 1 134 -> 1 041 MiB (ниже тогдашнего потолка 1 116). Цена - второй
   пересчёт attention (+9% к циклу на стресс-срезе, где такие все шаги); на обычных шагах режим не
   включается, их результат побитно тот же.
5. **Слитая голова кусками словаря** (`5c93f07`). Вес `lm_head` (151 936 x 1 536) лежит на хосте
   и едет на GPU кусками по 8 192 строки словаря в три буфера по отдельному CUDA stream; первые
   копии стартуют ещё на последних трёх слоях forward. Для каждого куска: GEMM `lm_head` (cuBLAS)
   по всем строкам шага, затем `lm_head_piece_kernel` обновляет online-состояние каждой строки
   (максимум, сумма exp, сумма exp * logit, argmax) и для строк с целевым токеном накапливает в
   fp32 градиент по скрытому состоянию `sum_v exp(logit_v - max) W_v` с пересчётом при росте
   максимума. После последнего куска `lm_head_finish_kernel` выдаёт loss, энтропию, accuracy и
   градиент. Метрики TRL/Soup и loss строк для rewind считаются в том же проходе. Строки промпта
   (~37% токенов) получают только энтропию и argmax: градиент через матрицу головы для них не
   считается. **Не побитно:** loss совпадает с вариантом "вес на GPU, один проход по словарю" до
   ~1e-7, но не побитно - GEMM кусками словаря суммирует в другом порядке, и у части логитов
   расходится 1 ulp fp16. Кривая loss и eval loss против базы от этого не изменились (0,01% / 0,04%).
6. **Веса слоёв в pinned-памяти CPU с момента загрузки** (`f041159`, `solution/hostload.py`).
   bitsandbytes квантует каждый `Linear4bit` на GPU как обычно (тот же код, те же значения), и
   сразу после этого упакованные NF4-байты и absmax копируются на хост, а копия на GPU
   освобождается; на GPU остаётся только маленькое состояние двойной квантизации. Для этого мы
   патчим `transformers.modeling_utils.caching_allocator_warmup`: настройки аллокатора PyTorch не
   меняются (`expandable_segments` задаёт harness), мы лишь не даём transformers заранее
   резервировать GPU-память под веса, которые сразу уходят на хост. `model.to()` из accelerate эти
   веса не трогает.
   В шаге NF4-байты слоя копируются на GPU в один из трёх слотов по отдельному CUDA stream на слой
   вперёд (в backward - на слой назад), копия слоя (~24 MiB) идёт параллельно с GEMM. После
   обучения слоты освобождаются, а веса возвращаются на GPU только при первом forward-вызове
   4-битного слоя (сохранению LoRA-адаптера они не нужны).
7. **Эмбеддинг / `lm_head` в fp16 и на хосте** (`solution/offload.py`). peft не поднимает этот
   замороженный вес в fp32. Это без потерь: fp32-значения базы - точные копии fp16-чекпойнта, а
   `lm_head` база и так считает под autocast в fp16. Загрузчик кладёт этот вес сразу в память CPU
   (в карте устройств, которую читает загрузчик весов, только для эмбеддинга / `lm_head`), там он
   и остаётся весь прогон в pinned-памяти. Строки эмбеддинга шага выбираются на CPU, копируются на
   GPU и приводятся к fp32 (побитно как у базы); голова стримится кусками (п. 5).
8. **Фоновая компиляция кернелов.** С момента `apply()` (имя модели берём из того же `--config`,
   который читает Soup) поток того же процесса компилирует каждый вариант наших кернелов через те же
   функции, что и шаг обучения (ключи кэша Triton совпадают), и собирает их C-лаунчеры. Только
   компиляция, без запусков: модули CUDA грузятся на GPU при первом запуске в шаге, уже после пика
   загрузки модели (иначе они добавлялись к пику, замер: +36 MiB). Поток компиляции и запущенные им
   ptxas / gcc работают с nice 19 и берут только простаивающий CPU; поток один и стартует до импорта
   peft (на 2 ядрах Kaggle каждый следующий поток тормозил загрузку модели сильнее, чем ускорял
   компиляцию), C-лаунчеры собираются с -O0. Компиляция входит в замер, но идёт одновременно с
   импортами и загрузкой модели: на T4 ~7-8 с в фоне, обучение её обычно не ждёт, первый шаг -
   1,0 с вместо 8,5 с. Seed'ы dropout объявлены `do_not_specialize`, иначе
   Triton перекомпилировал бы кернел при seed, кратном 16.
9. **Метрики TRL и строки rewind пишутся после backward** (хук `on_pre_optimizer_step`): их чтение на
   CPU больше не останавливает GPU между forward и backward; значения и порядок записей те же.
10. **Меньше запусков на шаг.** Один fp16-буфер весов LoRA на шаг вместо 8 приведений на слой, одна
    деквантизация на [q|k|v] и одна на [gate|up], первый слой без backward по входу, split-K для
    backward через gate/up (K = 17 920 одним GEMM - 1,93 мс, четырьмя по 4 480 - 1,70 мс).

### Как подключается и что остаётся прежним

`solution.apply()` ставит патчи:

- `SFTTrainerWrapper.setup` - запуск фоновой компиляции, если она ещё не идёт;
- загрузка модели в transformers (`offload.py`, `hostload.py`) - эмбеддинг / `lm_head` сразу в
  память CPU, NF4-веса на хост сразу после квантования; только для Qwen2, которую bitsandbytes
  квантует в NF4 на одном GPU на fp16-пути Soup;
- `peft.prepare_model_for_kbit_training` - эмбеддинг Qwen2 остаётся в fp16;
- `SFTTrainerWrapper.train` - если модель распознана и это fp16-путь Soup на GPU sm_70+ (класс
  T4; условие ниже), подменяет `compute_loss` тренера. Новый
  `compute_loss` делает ту же бухгалтерию, что HF `Trainer` + TRL `SFTTrainer` + rewind-рекордер
  Soup: нормировка loss по `num_items_in_batch`, `entropy` по всем реальным токенам, `num_tokens`,
  `mean_token_accuracy` по токенам ответа, строки `rewind.jsonl` с loss каждой строки;
- патчи накладных расходов запуска (следующий раздел).

**Откат на код Soup** (`b2fdaac`). Всё, что слитый шаг не берёт, уходит в исходный `compute_loss`
без изменений: фейковые модули в тестах Soup, eval-режим, лишние ключи во входах, `label_smoother`,
другие архитектуры. Если откат случается уже после слитых шагов, 4-битные веса сначала
возвращаются на GPU. Если шаг не установился, а модель уже загружена с весами на хосте, перед
обучением кодом Soup все веса (NF4 и эмбеддинг) возвращаются на GPU (`hostload.restore`,
`offload.restore_embeddings`). Батч, который шаг не поддерживает (левый паддинг), отклоняется исключением
`UnsupportedBatch` до того, как шаг что-либо изменил, и тоже идёт в исходный код. Если наш шаг не
установился вообще, fp32-копия эмбеддинга восстанавливается и обучение идёт целиком кодом Soup.
Это покрыто тестами `solution/test_fallback.py`. В фиксированном конфиге кейса эти ветки не
срабатывают, но организаторы просят откат для неподдерживаемых входов
([t.me/souptasterschat/576](https://t.me/souptasterschat/576)).

**Только fp16-путь на GPU класса T4** (`20206f1`). Слитый шаг и фоновая компиляция включаются,
только если Soup обучает в fp16 (`fp16=True`, `bf16=False`) на GPU sm_70 или новее без bf16 - как
на T4. На GPU с bf16 (A100, L4, H100) Soup обучает в bf16, а наш шаг считает в fp16 и поменял бы
dtype вычислений, что запрещено ([t.me/souptasterschat/620](https://t.me/souptasterschat/620)). На
картах старше sm_70 (например, P100) Triton не работает. В обоих случаях идёт исходный код Soup, а
наши кернелы даже не компилируются.

Не меняются: модель, данные, батчи и их порядок, число шагов, LoRA (r, alpha, dropout 0,05,
целевые модули), оптимизатор и расписание lr, настройки тренера, выходы Soup, аллокатор.
Обучаемых параметров не добавляется: градиенты LoRA возвращает наш `autograd.Function`.

## Патчи накладных расходов запуска (не кернелы)

Замеряется вся команда `soup train`, поэтому кроме шага обучения мы убрали лишнюю работу самого
запуска и тренера HF на границе шагов. Организаторы подтвердили, что ускорение не обязано идти только от шагов обучения, и
попросили описать каждый такой патч ([t.me/souptasterschat/592](https://t.me/souptasterschat/592)).
Это работа на CPU: к доле наших кернелов (проверка 4) она не относится. Все патчи действуют только
внутри замеряемого запуска, ничего не сохраняют между запусками и ведут себя одинаково под замером
и в тестах (79 тестов Soup проходят с ними). Заглушек в `sys.modules` нет.

| Патч | Где | Что делает | Эффект на T4 |
|---|---|---|---|
| Снимок `packages_distributions()` | `patch.py`, `patch_library_overheads` | `importlib.metadata.packages_distributions()` обходит все установленные пакеты (~2,3 с на образе Kaggle). transformers вызывает её при импорте и хранит результат в `PACKAGE_DISTRIBUTION_MAPPING`, импорт trl вызывает её ещё раз. Мы снимаем копию словаря transformers и отдаём каждому следующему вызывающему его собственную копию: результат тот же (пакеты во время запуска не ставятся), а изменения одного вызывающего не видны другим - условие из [t.me/souptasterschat/592](https://t.me/souptasterschat/592) | -2,3 с |
| bitsandbytes импортируется с `TORCHDYNAMO_DISABLE=1` только на этот импорт | `startup.py`, `import_bitsandbytes` | bitsandbytes оборачивает несколько CPU-путей в `torch.compile`, и при импорте тянет компилятор TorchInductor (~150 модулей), который этот запуск не использует: на CUDA у каждой операции bnb свой кернел. Переменная читается только в момент вызова `torch.compile`, сразу после импорта мы возвращаем её прежнее значение; путь обучения, harness и проверки не меняются. Разрешено: [t.me/souptasterschat/834](https://t.me/souptasterschat/834) | -1,2 с |
| Импорт без scikit-learn и (без `--wandb` / `--tracker`) без wandb | `startup.py`, `import_without_sklearn`, `import_without_wandb` | transformers импортирует sklearn в двух модулях только ради функций, которых обучение не использует (подбор порога assisted generation, GLUE-метрики); trl импортирует wandb в трёх модулях при импорте, даже если Soup ни во что не логирует (`report_to="none"` без этих флагов). Библиотеки просто не импортируются, как на машине без них. Разрешено: [t.me/souptasterschat/622](https://t.me/souptasterschat/622) (не грузить ненужную библиотеку можно), заглушки в `sys.modules` запрещены ([t.me/souptasterschat/609](https://t.me/souptasterschat/609)) - их нет | -1,05 с |
| Фоновая компиляция не отнимает CPU у загрузки модели: nice 19, один поток, старт до импорта peft, лаунчеры с -O0 | `warmup.py`, `__init__.py` | На Kaggle 2 ядра x 2 потока, и компиляция Triton (LLVM, ptxas, gcc для лаунчеров) отнимала CPU у загрузки модели Soup: с прогревом она шла 6,1 с, без него 3,0 с (GIL тут ни при чём: py-spy `--gil`). `os.setpriority` по native id потока: на Linux приоритет у каждого потока свой и наследуется дочерними процессами ptxas / gcc, и компиляция берёт только простаивающий CPU. Один поток вместо трёх, зато стартует на ~1,5 с раньше (до импорта peft, после проверок sklearn / bitsandbytes). C-лаунчеры собираются через официальный хук Triton `knobs.build.impl` с -O0 (только пока идёт прогрев): это флаги сборки C-обвязки, которая запускает наши Triton-кернелы, а не PyTorch и не сами вычисления; код кернелов (PTX / cubin) тот же. Прогрев на ~1,5 с короче, цикл не медленнее. Всё по-прежнему в том же процессе и внутри замера | nice: -0,6 с; один поток и ранний старт: -1,3 с; -O0: прогрев 8,7-9,7 -> 7,0-7,9 с |
| Обходы модели на границе шага по спискам, снятым один раз (`f2fd8a2`, `9b65cde`) | `patch.py`, `_walk_model_once` | Тренер HF на каждом шаге 4 раза обходит всю модель (~1 000 модулей, ~700 параметров, почти все замороженные): `num_parameters()` для счётчика FLOP в логе, `model.parameters()` для клиппинга градиентов, `zero_grad()` и `model.train()`; в трейсе T4 это ~27 мс пустого GPU между шагами, большей частью чистый Python. Теперь эти обходы идут по спискам модулей и параметров, снятым один раз при установке шага: те же параметры в том же порядке передаются тому же коду HF / torch. `num_parameters` запоминается по своим аргументам; исходный `train()` вызывается, только если какой-то модуль не в нужном режиме (сверх флагов он что-то делает лишь при смене режима). Оптимизатор, клиппинг и GradScaler не тронуты; `total_flos`, `grad_norm` и loss совпадают. Основание - [t.me/souptasterschat/592](https://t.me/souptasterschat/592) (сопутствующие ускорения при тех же результатах) | цикл 25,72 -> 25,12 с, вся команда -0,75 с, пик тот же (Brev T4, A/B по 4-8 запусков; проверки 10/10) |

**От чего отказались: случайный `new_fingerprint` для `datasets.Dataset.map`.** Для датасета в
памяти `map` хэширует функцию преобразования через dill только ради имени кэш-файла, который не
записывается, а функции Soup замыкают токенизатор (~2,1 с на запуск). Организаторы сначала
допустили подмену fingerprint при условиях ([t.me/souptasterschat/592](https://t.me/souptasterschat/592)),
но позже на такой же вопрос ответили, что это изменение данных
([t.me/souptasterschat/1548](https://t.me/souptasterschat/1548)). Мы убрали патч (`1f255db`):
~2 с не стоят риска недопуска.

## Почему это по правилам

Каждый приём, который можно счесть "серой зоной", и где он разрешён: раздел ТЗ, таймкод Q&A-панели
авторов кейса ([запись](https://www.youtube.com/live/sYAX128vRrQ)) и ответы организаторов в чате.

| Приём | Основание |
|---|---|
| Свой `torch.autograd.Function` на слой и патчи transformers / peft / bitsandbytes / Soup в `apply()` | ТЗ п. 3-4 ("подключаются одной функцией apply()"); README шаблона "How your code plugs in"; панель 43:04; своя деквантизация вместо bitsandbytes - [t.me/souptasterschat/609](https://t.me/souptasterschat/609) |
| Удаление pad-токенов внутри батча, varlen attention | ТЗ п. 8 ("убирать pad-токены внутри батча своим кодом можно"); панель 12:22; встроенная в PyTorch varlen-функция с `cu_seqlens` - не запрещённая библиотека, своим кернелом не считается ([t.me/souptasterschat/1632](https://t.me/souptasterschat/1632)) |
| Пересчёт слоя в backward | README шаблона: "recomputation or offloading in your own code (its time counts)"; панель 44:10-44:48 (запрещён только встроенный флаг Soup) |
| NF4-веса слоёв в pinned-памяти CPU с подкачкой на GPU, на хост - сразу после квантования при загрузке | "собственный CPU offloading" замороженных весов - разрешён ([t.me/souptasterschat/834](https://t.me/souptasterschat/834)); перенос `Params4bit.data` на CPU после сборки модели - "да" ([t.me/souptasterschat/1535](https://t.me/souptasterschat/1535)); квантование - тот же код bitsandbytes, байты те же, меняется только место хранения ([t.me/souptasterschat/620](https://t.me/souptasterschat/620)) |
| Эмбеддинг / `lm_head` весь прогон в pinned-памяти CPU, голова стримится на GPU кусками каждый шаг | прямо этот случай: замороженные `embed_tokens` / `lm_head` в pinned-памяти на весь прогон с подкачкой головы кусками - "собственный CPU offloading", время копий входит в замер ([t.me/souptasterschat/834](https://t.me/souptasterschat/834)); вычисления в fp16, как у базы под autocast ([t.me/souptasterschat/620](https://t.me/souptasterschat/620)) |

| Патч загрузчика transformers (куда класть веса при загрузке) | патчи transformers в `apply()` - панель 43:04 ("через apply можно подменять код модели и операции"); значения весов и вся остальная загрузка те же, `hf_device_map` и dispatch модели не меняются; встроенный в Soup `activation_offloading` и другие его режимы не используются |

| Кернелы без `tl.dot` | свои `@triton.jit` из `solution/` - проверки 3-4; панель 40:59-41:09 |

Чего мы не делаем: не включаем режимы Soup (`use_cut_ce`, `use_liger`, `gradient_checkpointing`,
`activation_offloading`...) и не вызываем их внутренние реализации; не используем внешние
кернел-библиотеки; не запускаем отдельных процессов; не храним ничего между запусками; не меняем
аллокатор; не пишем в `sys.modules`; не завершаем процесс через `os._exit`; не ведём себя иначе
под замером (патч срабатывает по типу модели, а не по окружению). int8-GEMM организаторы разрешили
([t.me/souptasterschat/1587](https://t.me/souptasterschat/1587)), но мы его не взяли - см. эксперименты.

## Как запустить

### Kaggle (как жюри)

1. Kaggle -> Create -> New Notebook -> File -> Import Notebook -> `templates/kaggle_notebook.ipynb`
   из этого репозитория. Или откройте наш сохранённый ноутбук (ссылка в начале) и нажмите Copy & Edit.
2. Справа: Accelerator **GPU T4 x2**, Internet **on** (нужен аккаунт с подтверждённым телефоном).
3. В первой ячейке:
   ```python
   REPO_URL = "https://github.com/BAITC-Hacks/hack-fe30cb28-opus-5-5-ultracode.git"
   COMMIT = "[финал]"
   ```
4. Run All. Ноутбук ставит закреплённые версии пакетов, готовит данные, гоняет тесты `solution/`,
   затем `harness/run_task.py` (база и решение) и `harness/check_rules.py`. Итоговая таблица
   печатается в выводе, файлы - `runs/result.json` и `runs/checks.json`.

Больше ничего делать не нужно: решение подключается через `solution.apply()`, ручных правок и
переменных окружения нет. В нашем сохранённом ноутбуке можно сверить вывод с таблицей выше.

### Локально (Linux + NVIDIA T4, или другой GPU для тестов)

```bash
pip install "soup-cli[train]==0.77.0" "transformers==5.16.1" "peft==0.20.0" "trl==0.29.1" \
    "bitsandbytes==0.50.2" "accelerate==1.14.0" pytest
python task/prepare_data.py
python -m pytest solution -q          # кернелы против PyTorch, весь шаг против HF + PEFT, откат
SOUP_APPLY_SOLUTION=1 python -m pytest tests -q -p no:cacheprovider   # 79 тестов Soup с apply() (проверка 10)
python harness/run_task.py --repeats 2
python harness/check_rules.py
```

Повторять замер нужно на T4. **На Ampere и новее (RTX 30xx/40xx, A100, L4, H100) слитый шаг
сам не включается, так и задумано** (`20206f1`): Soup там обучает в bf16, и в логе решения будет
`[solution] not the fp16 training path of a T4-class GPU ...: training with the original code path`.
Это не поломка - обучение идёт исходным кодом Soup, со временем и памятью базы. Тесты `solution/`
(24, включая откат) и 79 тестов Soup на таких GPU проходят: они не зависят от пути обучения
(проверено на RTX 4060 после `20206f1`).

Чтобы посмотреть сам слитый шаг на bf16-GPU, Soup нужно принудительно перевести на его fp16-путь,
как на T4. Мы делали это обёрткой только для локальной отладки (в решение она не входит):

```python
# fp16_path.py: запуск harness/_train.py так, будто GPU не поддерживает bf16
import runpy, sys
import soup_cli.utils.gpu as gpu

gpu.cuda_supports_bf16 = lambda: False  # Soup выбирает fp16, наше решение видит fp16-путь T4
sys.path.insert(0, "harness")
sys.argv = ["harness/_train.py"] + sys.argv[1:]
runpy.run_path("harness/_train.py", run_name="__main__")
```

Конфиг делаем напрямую из `task/task.yaml`, как `run_task.py`, но без прогона базы: базе нужно
~14 ГБ, на картах с 8-12 ГБ она упадёт с OOM.

```bash
python task/prepare_data.py
python -c "import os, yaml; c = yaml.safe_load(open('task/task.yaml')); c['data']['train'] = 'data/train.jsonl'; c['output'] = 'runs/local/adapter'; os.makedirs('runs/local', exist_ok=True); yaml.safe_dump(c, open('runs/local/task.yaml', 'w'))"
python fp16_path.py --config runs/local/task.yaml --metrics runs/local/metrics.json --solution
```

Проверено на RTX 4060 (8 ГБ): шаг ставится, 64 шага, пик 1 152 MiB. Засчитываемые замеры - только
на T4.

### Регуляторы (`solution/patch.py`)

| Регулятор | По умолчанию | Что делает |
|---|---|---|
| `OFFLOAD_HEAD` | `True` | эмбеддинг / `lm_head` весь прогон в pinned-памяти CPU, голова кусками словаря; `False` - вес на GPU (пик ~1 233 MiB, loss побитно как у прохода по всему словарю) |
| `HOST_NF4_AT_LOAD` | `True` | NF4-веса на хост сразу после квантования при загрузке модели |
| `OFFLOAD_WEIGHTS` | `True` | подкачка NF4-весов из pinned-памяти CPU в шаге; `False` - веса на GPU (до выгрузок при загрузке пик был 1 761 MiB против 1 385, цикл тот же) |
| `STEP_CAP_MIB` | `None` | явный потолок памяти шага (MiB allocated) вместо расчётного |
| `EXTRA_MEMORY_MIB` | 0 | сколько MiB шаги могут занять сверх расчётного потолка под хранение активаций вместо пересчёта (обмен памяти на скорость) |

### Тесты корректности

- `solution/test_kernels.py`: каждый кернел против PyTorch, forward и backward; NF4-деквантизация
  побитно против `bitsandbytes`, в том числе на весе полного размера; varlen attention против SDPA
  по каждой строке; **весь шаг против HF + PEFT под fp16 autocast** на маленькой 4-битной Qwen2
  (loss до 2e-6, градиенты LoRA до 0,1-0,5% - уровень шума fp16); стриминг весов, хранение
  gate/up и полное хранение дают побитно те же loss и градиенты, экономный шаг - те же с точностью
  до разбиения GEMM на куски; `restore` возвращает веса побитно.
- `solution/test_fallback.py`: откат на код Soup в eval-режиме, с лишним ключом во входах, при
  левом паддинге и в цепочке train - eval - train после слитых шагов.
- `solution/test_hostload.py`: NF4-веса, выгруженные на хост при загрузке, - те же значения, тот же
  слитый шаг, и исходный путь Soup после `restore()`.
- `solution/test_host_head.py`: голова кусками с хоста против головы с весом на GPU, весь шаг с обеими
  выгрузками.
- 79 тестов Soup с нашими патчами (`SOUP_APPLY_SOLUTION=1`).

## Ограничения и что не получилось

- **Решение заточено под этот кейс:** Qwen2 (RoPE `default`, без sliding window), веса NF4 из
  bitsandbytes, LoRA только на `q_proj`/`v_proj`, fp16-путь Soup на GPU sm_70+ без bf16 (T4).
  Всё остальное идёт исходным кодом Soup без ускорения - корректно, но медленно. В том числе на
  bf16-GPU (A100, L4, H100) решение не ускоряет ничего: Soup там обучает в bf16, а наш шаг
  считает в fp16, и сменить dtype вычислений нельзя
  ([t.me/souptasterschat/620](https://t.me/souptasterschat/620)). bf16-вариант шага мы не делали.
- **Скорость - наша слабая сторона.** GEMM cuBLAS занимают ~69% работы GPU в шаге и уже на потолке
  T4; свой GEMM на Triton для sm_75 без тензорных ядер не получился (см. эксперименты). Пересчёт
  слоя стоит до ~20% цикла, мы сознательно платим им за ~6x меньше памяти активаций.
- **Вне цикла обучения мы выигрываем мало.** Импорты, загрузка модели, сохранение и выход - почти
  те же, что у базы; патчи запуска дают ~-6 с, а фоновая компиляция даже с nice 19 в одном потоке
  ещё отнимает ~1 с у загрузки модели (2 ядра x 2 потока). Остальное - не наше и есть у базы:
  `packages_distributions()` внутри `import transformers` в харнессе до `apply()` (2,3 с),
  хэш токенизатора в `datasets.map` (2,1 с, fingerprint трогать нельзя), ленивая загрузка ~78
  модулей CUDA кернелов PyTorch в первом шаге (~0,4 с) и завершение интерпретатора (~1,7 с, у базы
  1,72 с). На машинах с быстрым CPU (Brev) время вне цикла у нас и у базы почти одинаковое.
- **Дальше 813 MiB пик опускается плохо.** ~165 MiB - вне аллокатора PyTorch (CUDA-контекст,
  модули кернелов и cuBLAS), ещё ~150 MiB - слоты весов слоя и буферы кусков головы, остальное -
  активации шага, которые уже держит потолок. Чтобы опуститься заметно ниже, пришлось бы
  пересчитывать больше и платить скоростью.
- **Выгрузка головы зависит от PCIe.** На Kaggle (~13 ГБ/с) она бесплатна по времени, на Brev
  (~6,3 ГБ/с) стоит ~2,4 с: шаг ждёт копий кусков головы (268 мс копий на шаг). Резидентные на GPU
  куски головы (4 и 8 по 24 MiB) цикл не ускорили, а пик подняли - не взяли.
- **Длинные батчи медленнее.** Экономный шаг удерживает пик, но на батчах ~1 870+ токенов
  пересчитывает attention дважды: на стресс-срезе из одних таких батчей цикл +9%.
- **Speedup шумит между инстансами T4** (база 78-97 с на Kaggle, 67-69 с на Brev), поэтому
  speedup одной сессии нельзя переносить на другую; память стабильна.
- **Энтропия и loss строк считаются в fp32** (в базе часть этих величин округляется до fp16):
  расхождение с базой - сотые доли процента, в допусках проверки 5.
- **Loss не побитно равен варианту без выгрузки головы:** GEMM головы кусками словаря суммирует в
  другом порядке (1 ulp fp16 у части логитов, loss до ~1e-7). Против базы все проверки проходят.
- **Что не успели:** GEMM на тензорных ядрах T4 через PTX `mma.sync` внутри Triton (вопрос
  организаторам остался без ответа) - главный оставшийся рычаг скорости; bf16-вариант шага для
  Ampere и новее.
